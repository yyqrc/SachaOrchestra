# 合并结果核对

仅在评审对象包含合并结果、冲突处理或旧分支同步时读取。这里补充基线取得与语义比较方法，评审职责、授权和结果沿用 Skill 正文。

1. 核实用户指定结果的父提交、两侧身份和共同祖先；父提交顺序不代表新旧或权威。未完成合并可从 `git ls-files -u` 取得冲突文件的共同起点与两侧输入，另核对实际合入目标；已提交合并用 `git show -s --format='%H %P' <merge>`、`git merge-base --all <side-a> <side-b>` 和 `git show --remerge-diff <merge>`。后者用于查看冲突解决选择，不代表全部合并影响。共同起点不唯一或输入不可取得时，说明比较缺口，不静默选择一个起点。
2. 在本次受影响的规则及直接使用方内，分别比较共同起点到两侧、两侧到最终结果。根据实际差异核对已精简、迁移或撤回的行为、仍有效的新决定及合入方的合法新增；某条文本较旧、来自某一作者或属于某一父提交，均不足以决定保留或删除。需要追溯时只查引入或撤回该行为的具体提交；合入方已包含更早合并时，沿相关变化查那次合并，不把整段历史归给最后一次提交。
3. 把冲突解决区域与同范围内自动合并、无文本冲突的变化一起核对：最终条件、动作、停止和恢复边界是否仍符合两侧有效决定，负责定义与直接消费者是否一致。规则删除或迁移后，检查旧位置或消费者是否带回原行为；不能因冲突标记已清除或差异能干净应用而判断通过。不扩大到无关历史或全仓规则。
4. 报告问题时给出共同起点、有效变化来源和最终位置，区分旧行为回流、新增缺陷与应保留的新增；不混算同一回退链，也不建议整侧覆盖。

可用 `git diff <base> <side> -- <paths>` 与 `git diff <side> <result> -- <paths>` 重放上述比较。没有 Git 对象但有已核实的四份快照时，可用相同范围的快照差异核对，并说明来源与取证限制。
