# Sacha 文档治理

## 功能

在明确范围内判断每份文本供谁使用、内容应写在哪里、哪些现有内容依赖它，以及安装后能否读取；精简文字时保留所有会改变判断或行动的含义，并把历史材料与当前有效内容分开。

## 先确定范围和用途

1. 要求用户给出目标路径、差异或明确子树；范围不清时停止，不推导全仓审计。
2. 先读[项目规则](../../../AGENTS.md)。目标位于 `docs/**` 时再读[开发文档规则](../../../docs/AGENTS.md)和适用的 [`CONTEXT.md`](../../../docs/CONTEXT.md) 条目；目标位于 `plugins/sacha-orchestra/**` 时读取定义相关安装后行为的文件及其直接引用方。
3. 只有入口、节点、连线、角色或技能职责、内容归属可能变化时读取 [`PLUGIN_DESIGN.md`](../../../PLUGIN_DESIGN.md)；普通局部文本不借此扩大范围。
4. 目标是技能或适配器文本时，读取[技能与适配器文本](references/skill-and-adapter-text.md)；其他文档不加载该参考说明。

## 整理和核对

1. 先按路径判定文本用于插件开发、随插件发布、记录任务还是提供测试输入；一份文档只保留一种用途。随插件发布的本地引用必须位于部署清单解析出的发布 `root` 内。
2. 根据谁会使用内容，区分用户可读叙述、正式标识、代码与机器合同。面向用户的流程和维护叙述使用自然中文，不得连续堆叠内部英文术语或用未解释缩写承载关键判断；产品、角色（Role）、技能（Skill）、运行环境（Runtime）、API、字段、枚举、状态和已经明确归属的术语按原标识保留，中文可能产生歧义时首次写作“中文（英文原词）”。不得用关键词扫描代替语义判断。
3. 确定每项事实由哪个文件完整定义，以及哪些现有内容会使用它。现有文件能够承载时只修改该处，其他位置改为最短指向或链接，不新建平行说明。
4. 改写前逐项列出需要保留的主体、触发或进入条件、动作及先后依赖、结果或限制、规范强度、退出、停止与恢复、例外、负责文件、用户决策点、使用方、授权、安全、失败或未验证状态、证据、验收、进入条件（Entry Condition）和数据格式（schema）；只有这些事实全部保留且含义唯一时才压缩。
5. 只保留会改变内容归属、使用方、流程判断、授权、安全、恢复、验收、证据或维护动作的限制；删除背景铺垫、常识、历史、反向释义、同义重复和没有实际用途的说明。
6. 遇到依赖会话视角、评审过程、临时计划编号、不可达草稿引用或控制流程的叙述时，检查仓库读者能否在不依赖对话、PR 线程或未提交草稿的情况下解析引用并验证事实。不能时把真实事实改写为当前状态并删除过程叙述；没有事实的过程文本直接删除。
7. 不把现行机制的历史、生成结果或测试清单手写进负责定义机制的文件。生成内容应修改其来源；源码、发布包或缓存、实际运行和用户验收分别报告，不互相替代。
8. 移动、删除或标记取代前核对引用关系和完整取代关系。历史工作记录（Artifact）只在仍会误导当前操作时增加最短的“历史或已取代、当前负责文件”入口，不改写冻结正文。
9. 复核相邻文本是否依赖同一语义；只处理实际使用方，不扩成没有明确用途的语料库清理。

## 输出

- 报告实际检查或修改范围、文档用途、完整定义所在文件、现有使用方、完成的迁移或精简、刻意保留的内容、冲突和未验证部分。
- 用户只要求审查时只报告发现；获授权的修改使用真实统一差异（unified diff），并运行适合目标文件的最小验证。

## 何时停止

- 文本变化会改变产品入口、流程、角色或技能职责、授权、验收或破坏性边界时停止写入并交用户确认，不把语义变化伪装成文案整理。
- 改写后需要依赖上下文猜测、存在会改变判断的多种合理解释或无法证明语义等价时保留原文；不能用补充解释掩盖不确定语义。
- 不用关键词、固定句子、段落顺序或字数证明语义；不因“更完整”增加规则、工作记录（Artifact）、字段或校验器。
- 本技能不执行项目文档生成、实际运行场景、发布、安装、Git 写入或外部动作。
