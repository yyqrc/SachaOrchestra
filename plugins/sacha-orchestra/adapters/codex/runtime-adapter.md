## 2. Codex 工具调用

用户交互、独立任务和子代理分别使用各自的工具。

| 动作 | Codex 工具或通道 | 约束 |
| --- | --- | --- |
| 向用户提问 | 当前宿主允许的提问工具或普通文本 | 按[交互规则](../../core/human-interaction-contract.md#3-human-决定与对话同步)选择方式。若 `request_user_input` 仅支持可选澄清，必要信息和批准改用宿主允许的方式 |
| 向用户报告进度 | `commentary` | 展示核心规则要求报告的新事实、风险、阻塞或计划变化 |
| 用户最终答复 | `final` | 按 [交互规则](../../core/human-interaction-contract.md#2-信息顺序与可见性) 交付当前任务结果 |
| 独立任务创建与发送消息 | `list_projects`、`create_thread`、`send_message_to_thread` | [调用参数与授权](#23-独立任务创建与消息发送) |
| 查找已有独立任务 | `read_thread`、`list_threads` | [按原标识核对或分页查找](#232-查找已有独立任务) |
| 独立任务启动或结果核对 | `wait_threads` | [路线图后续规划](#231-路线图后续-sacha-planner-任务)、[依赖等待](#26-依赖等待) |
| Antigravity 外部 Agent | 当前主任务可用的本地命令工具与 [ACP 客户端](scripts/agy_acp.py) | [选路、派发与续接](#32-antigravity-acp) |

### 2.1 核对当前会话的工具

主任务与各子代理分别以本会话实际提供的工具声明、可发现的类型及参数为准，在既有范围和授权内执行。创建、恢复、上下文压缩或重连后，执行前核对受影响的能力，沿用仍有效的结果。源码、安装缓存、磁盘配置、独立 CLI、其他会话和 App Server 协议各自只能证明对应范围的能力。

首次派发子代理时，只核对[创建所需的类型和参数](#c-首次创建参数)及本次工作需要的协作工具。其他工具用到前再核对。独立任务按本次动作核对所需的桌面工具。接口、必需参数或能力缺失、冲突或无法确定时，按[错误与恢复](#31-错误与恢复)处理。

派发可能写入的工作或让原代理继续这类工作前，先确认 `interrupt_agent` 可用，并确定可用哪些状态或结果核实写入已停止。如果进程、任务或工具可能在回合中断后继续写入，还要确认能停止这些操作并核实状态。缺少必要能力时，只暂停受影响的写入派发。

### 2.2 子代理调度

主任务为 Planner、Reviewer、Executor、Explore 研究和普通工作单元按第 3 节组装首次创建参数。角色是评估工作单元的输入，实际工具只决定如何传递。Manager 留在主任务内。委派代理按下表交换事实或返回协调请求，创建、继续驱动和中断代理由主任务负责。

| 动作 | 协作工具 | 约束 |
| --- | --- | --- |
| 首次创建 | `collaboration.spawn_agent` | 仅主任务调用，每个工作单元至多一次；参数按第 3 节 |
| 运行中补充或调整 | `send_message` | 主任务沿用同一标识、负责方和连续目标。独立单元按[协调规则第 2 节](../../core/coordination-contract.md#2-评估拆分依赖与就绪判定)新建 |
| 委派代理交换事实或返回协调请求 | `send_message` | 只向已知主任务或同级发送协调规则允许的信息。分配工作以及启动、继续或中断代理由主任务处理 |
| 已结束回合后继续 | `followup_task` | 仅主任务调用。满足协调规则第 2 节的复用条件时使用原标识，否则按第 3 节新建 |
| 等待 | `wait_agent` | 仅主任务在真实依赖处等待；通知或超时不等于进程终止 |
| 中断当前回合 | `interrupt_agent` | 仅主任务在取消、失活或继续会增险时使用；代理仍可接收后续消息 |
| 核对与恢复标识 | `list_agents` | 仅主任务有界查询原目标；无唯一标识时停止，不创建替代写入者 |
| 代理完成后处理结果 | 沿用完成通知 | 使用返回结果，保留原始标识和证据 |

`followup_task` 继续原代理并保留其历史。首次创建的 `fork_turns="none"` 只控制是否继承父任务历史。主任务通过消息交付后续信息，新建时按第 3 节提供完整输入。

容量以当前宿主工具说明和实际状态为准，区分并发槽位、主任务是否占位与累计创建限制，不硬编码数量或推断未声明的累计上限。达到容量时按真实依赖等待，或由主任务处理适合的短小动作；不得为绕过容量把独立工作塞入旧代理，也不假定回合结束或中断必然释放槽位。

`interrupt_agent` 回执只证明当前回合已中断。按[单一写入者规则](../../core/coordination-contract.md#3-派发等待取消与单写入者)，从代理状态及相关进程、任务或工具的实际结果核实停写。分别记录回合中断和停写状态。

### 2.3 独立任务创建与消息发送

按各入口的条件确定可以新建后，再核对用户已经明确授权创建符合该用途的独立任务。已有证据覆盖该次创建时直接沿用。随后按以下步骤调用 `create_thread`。

1. 按已确认的工作位置填写 `target`。
   - 仓库工作先调用 `list_projects({})`，按工作目录、宿主和项目身份唯一确定目标。用返回的 `projectId` 填写 `target={type:"project", projectId, environment:{type:"local"}}`，默认用项目现有检出目录。只有用户明确要求 worktree 且项目的 `isGitRepository=true` 时才用 `environment.type="worktree"`。需要指定起点时，按用户要求和工具声明在 `environment.startingState` 中填写工作树或分支。
   - 项目无法唯一确定时先消歧。只有目标确实是本地无仓库工作且该入口允许时，才用 `target.type="projectless"`，有明确目录名时可传 `directoryName`。
   - 用户明确要求云环境时，先核对当前 `create_thread.target` 是否支持所需类型，再按其声明取输入。能够列出云环境或项目，只能证明可查询。当前会话只提供 `project` 和 `projectless` 时，按第 3.1 节报告缺口。
2. 将各入口要求的最小交接信息写入 `prompt`。这段话将作为目标任务中用户可见的首条请求，需说明目标、必要规则和输入、完成前的检查，以及用户打开任务时应看到的结果。可传简明的 `title`。只有用户已为该独立任务明确选择型号或推理强度时，才传对应且受支持的 `model` 或 `thinking`。第 3 节的自动选择只用于子代理。
3. 只提交一次创建请求。正式回执返回 `threadId` 和 `hostId`，用它们查询、等待或发送消息。若只返回 `clientThreadId`，只记录任务正在准备，交付状态仍待核实。从宿主记录确认同一任务的正式标识后，才能调用需要 `threadId` 的工具。向用户提供链接或原生标识，并按宿主要求输出对应的 `::created-thread{threadId="…"}` 或 `::created-thread{clientThreadId="…"}`。排队、失败或状态不明时按[错误与恢复](#31-错误与恢复)处理。

复用现有任务时，`send_message_to_thread` 要求有直接来自用户的明确授权，且授权能对应到这个唯一目标和本次消息。可沿用当前会话或其他可信证据中已核实的授权。另一任务发来的消息或要求回复的内容本身不构成用户授权。授权缺失或含糊时，发送前向用户确认。调用时传 `threadId`、已知的 `hostId` 和用户可见的 `prompt`，每次获准的交付只发送一次。省略 `model` 和 `thinking` 以沿用目标设置，只有用户明确要求且目标为 Codex 任务时才按当前声明设置它们。

#### 2.3.1 路线图后续 Sacha Planner 任务

按[工作流规则](../../core/workflow-contract.md#4-生命周期与-human-路由)核对该规划任务的明确创建授权，已有授权直接沿用。创建一个后续规划任务，`target.type="project"`，使用当前项目对应的已保存 Codex 项目。来源任务继续负责路线图，目标负责后续规划。

初始 `prompt` 明确写“使用 Sacha Planner”，要求冻结完整实施规格（Spec），并携带唯一路线图路径、候选规格的目标与范围、已确认决定、阻塞性未决项、只读边界和仍需授权的实施动作。目标自行读取项目规则、工作流规则和 [Planner 技能](../../skills/planner/SKILL.md)，按显式 Planner 请求启动。路线图正文、任务状态和其余未落盘对话留在来源任务。

取得正式标识后，调用一次 `wait_threads({targets, timeoutMs: 0})`，只传该目标，按第 2.6 节核对结果。快照还不能证明 Planner 已开始时，报告「任务已创建，启动尚未核实」并交付原目标引用。发现初始输入丢失、没有按请求规划或擅自开始实施时，报告偏差并保留同一目标。来源任务交付引用后结束。

#### 2.3.2 查找已有独立任务

1. 优先用已有的正式 `threadId` 和已知 `hostId` 调用 `read_thread`。按入口核对身份、状态和交接证据。只有 `clientThreadId` 或原请求状态仍不明时，沿用第 2.3 节和第 3.1 节核实同一次创建。
2. 需要继续查找候选时，用 `list_threads` 的 `mode: "history"` 在相关 Codex 宿主分页。按项目、反馈标识、已批准 Spec 等入口条件筛选结果。只对需要核实的候选调用 `read_thread`。同一 `source`、`hostId` 和 `archived` 用上次 `nextCursor` 作为本次 `cursor`。需要核对归档记录时另用 `archived: true`。
3. 证据能确定唯一结果时，沿用对应入口的复用、移交或 `no_op` 条件。只有证实没有匹配且已取得本次创建授权时才新建。最近列表没有命中、查找范围未覆盖或结果仍不明时，保留原标识和证据缺口，不据此新建。确实需要用户提供目标信息或决定选哪个任务时才询问。

### 2.4 用户发起的插件反馈

按[入口规则](../../core/intake-contract.md#41-用户明确调用)核对反馈授权，按[共用查找规则](#232-查找已有独立任务)取得匹配证据。根据[协调规则的反馈条件](../../core/coordination-contract.md#6-完成返回与偏差)，按第 2.3 节发送消息、创建任务，或在 `no_op` 时返回原任务引用。

发送和创建共用一份 `prompt`，包含具体反馈、必要规则和证据引用，以及由目标继续处理的说明。以工具结果核实反馈已交给唯一目标，再按第 2.6 节交付引用。移交失败或结果未知时按第 3.1 节核对原结果。

### 2.5 执行任务迁移

先按[工作流的迁移条文](../../core/workflow-contract.md#42-执行任务迁移)和[协调规则第 5 节](../../core/coordination-contract.md#5-executor-任务迁移)暂停写入并核对迁移前提，再按[共用查找规则](#232-查找已有独立任务)核实目标。按第 2.3 节向获准的原目标发送消息，或在确认无匹配且创建已获准时新建。

把协调规则要求的最小交接信息放入 `prompt`，包括项目规则、批准的 Spec、必要记录及证据的可读引用、宿主未提供的必要标识和接管职责。使用独立任务接管。完整历史分叉、`spawn_agent` 和委派代理都不能取得迁移标识。

用原生回执或目标记录核实同一目标已经收到交接信息，再按协调规则移交责任。交付失败或状态未知时按原标识核实。改为普通批准时，先用原请求、目标记录和写入者状态核实协调规则第 5 节的全部恢复条件，再恢复实施或写入派发。成功移交后的重复批准只返回原目标引用。

### 2.6 依赖等待

按[协调规则](../../core/coordination-contract.md#3-派发等待取消与单写入者)判断是否等待。移交责任后，来源任务交付目标链接或原生标识并结束。需要结果且接收方明确，或确需进行全新验证时，才等待独立任务的最终结果。路线图后续任务只核对启动，见第 2.3.1 节。

- 子代理依赖使用 `collaboration.wait_agent`。独立 Codex 任务使用 `wait_threads({targets, timeoutMs})`，单任务传一项，合并等待最多八项。每项传正式 `threadId` 及已取得的 `hostId`，续等时将各目标自己的返回游标传入 `targets[].afterCursor`。
- `timeoutMs: 0` 只取即时快照。任一目标的回合结束或需要关注时，等待可提前返回，收到当前用户的新输入也会结束等待。普通进度不会提前结束等待。按目标检查结果和 `errors`，再判断任务是否达到完成条件。若 `activityComplete=false`，活动记录可能不全。
- 调用等待前推进其他不依赖结果且不冲突的就绪工作。
- 等待时长在当前工具允许范围内兼顾宿主沟通要求与预计结果时间；通知可提前唤醒时，不为捕获完成而反复短等。没有可推进工作时沿用阻塞等待，不用定时消息催报或通过中断再继续探测进度。
- 进入等待时，按工作包预期耗时、最近实际活动和任务截止时间，确定下次确认代理是否仍在推进的时间。到这个时间前，`wait_agent` 可以超时多次。到时仍没有结果，或通知缺少会改变下一步的状态，才用 `list_agents` 查询已知目标。不要另建定时任务或定期催报。
- 等待超时或上下文压缩都不能证明代理已经失活。仍有有效进展时，更新下次核对时间并继续等待。
- 回合已结束但缺结果时，先读取可达的宿主结果。仍缺失时，只请求一次必要的结果或阻塞摘要。
- 状态不明或无进展时，先核对能观察到的工具和进程活动，再决定是否补问、恢复或取消。同一未知状态只延长等待间隔或按截止条件处理。禁止反复催报或因超时创建替代代理。取消和写入接管按第 2.2 节执行。
- 用已知的新事实向用户报告进度。报告进度本身不触发状态查询或重读相同记录。

### 2.7 客户端原生工具

优先使用当前会话直接提供的工具。工具发现、Code Mode、批量调用和结果收取直接按客户端原生接口及其加载条件执行。独立且就绪的调用可以并发，依赖前一步结果或判断时按顺序处理。

只读研究代理只用直接可见或搜索得到的只读工具，需要 shell、写入或调度时交回主任务。创建、继续、中断子代理等动作仍按第 2.2 节和宿主的直接调用限制执行。

工具不可达或无法唯一确定时，只暂停依赖部分。普通事实读取可用已核对输入、输出、副作用和授权的等价入口。接口身份属于验证目标、传输约束更严格或写入状态未知时，保留原入口。没有新依据时停止重复搜索。

已启动的调用按各层原生标识逐项收取结果。需要结果时，继续收取同一调用，直到取得可核实的最终结果。中间输出、超时或外层调用结束，均不能证明底层操作已完成或取消。按已有取消决定使用宿主工具取消，并核实底层任务已停止。缺少原标识或可核实结果时按[错误与恢复](#31-错误与恢复)处理。

## 3. 子代理类型、模型与推理强度

本节说明子代理的能力、模型和推理强度怎样选择。主任务的模型和强度由用户和宿主控制。派发前的工具检查见第 2.1 节。

### A. 选择依据

- 先核对用户明确指定的型号和强度适用于哪个任务和阶段。创建或迁移主任务时指定的设置默认限于该主任务，写入交接文本也保持原范围。只有明确覆盖当前子代理、工作单元或整个任务时，才对子代理沿用指定设置。其余单元按 B 节自动选择。
- 子代理仅在用户明确要求当前单元及阶段用 Astra 时采用。即使规划阶段的 Astra 要求写入批准范围，实施与验收仍分别按各自阶段的明确要求或自动规则选择。适用的精确要求无法按原样执行时，按第 3.1 节停止调用。
- 只读研究、获授权实施和正式独立复核分别需要对应能力类型。角色不等于型号，正式复核的独立性不能由更强模型替代。
- 工作单元的输入完整、边界明确，且完成检查可独立执行时，可按有界工作单元处理。需要跨职责范围综合信息或集成，或仍需判断重要边界时，按范围较广的单元处理，并区分常规和高风险。
- 同时考虑实施范围和失败影响。涉及破坏性删除或覆盖、改变多个使用方共享的持久身份或数据含义，以及正确性依赖并发、兼容或跨系统生命周期时，至少按范围较广的单元处理。难以回退、跨系统耦合或存在关键冲突时按高风险处理。普通可重建文件的输出仍按其实际风险评估。
- 较大有效上下文的依据是多个模块、调用/数据链或约束必须共同参与判断。文件数量、仓库体积、累计 token、正式复核或发布名称本身不决定型号或强度。
- 输入、范围、写入者、完成检查或独立性无法可靠判断时停止派发。只保存会改变当前选择的事实，复用仍有效的评估。

### B. 按顺序选择模型和强度

从上往下采用首个符合条件的选项。按工作事实选择，沿用核心规则的状态和就绪条件。

| 适用条件 | 请求字段 |
| --- | --- |
| 用户直接指定，或已批准范围载明用户对当前子代理及阶段的精确要求，且符合 A 节 | 原样使用当前工具支持的型号与强度。额外参数不受支持时停止 |
| 无高风险、复杂集成、动态诊断或较大有效上下文需求的普通正式独立复核。范围较广的常规单元也可使用，须满足同样限制，且同类任务的有效实测表明 Sol 的完成成本或时延更合适 | `model="gpt-6.2-sol"`，`reasoning_effort="medium"` |
| 有界单元。固定步骤和直接核验用 `high`，需结合多条已知条件判断用 `xhigh`，边界已定且须推导并核验多步相互依赖的结论用 `max` | `model="gpt-6.1-terra"`，`reasoning_effort` 按左列选择 |
| 范围较广的高风险单元，包括相应独立复核 | `model="gpt-6.2-sol"`，`reasoning_effort="max"` |
| 范围较广的常规单元，且需要复杂集成、动态诊断或较大有效上下文，包括相应独立复核 | `model="gpt-6.2-sol"`，`reasoning_effort="xhigh"` |
| 其余范围较广的单元，包括跨模块综合及相应独立复核 | `model="gpt-6.2-sol"`，`reasoning_effort="high"` |

同一有界单元的工作量增加或需要串行使用共享环境时，仍按其实际判断需求选择。

执行中发现已确认的前提不成立时，交回受影响的方案问题。困难、失败和反复尝试都不触发自动提高强度。满足协调规则第 2 节复用条件时保留原模型，新建时按本节选择。比较成本时，使用实际输入、缓存、输出、耗时与返工，并核对宿主计费口径。跨模型或新代理的缓存命中以实测为准。沿用仍有效的对照结果，数据不足时不宣称切换更省。不得按单价、累计 token 或固定阈值自动切换。

### C. 首次创建参数

| 单元 | `agent_type` | 能力边界 |
| --- | --- | --- |
| 只读研究 | `sacha_researcher` | 只接收研究就绪（`research-ready`）的单元及其必需的只读工具 |
| 实施与验证 | `sacha_executer` | 只接收已有授权且执行就绪（`execution-ready`）的单元，沿用父任务实际权限边界 |
| 正式独立复核 | `sacha_reviewer` | 未参与当前方案和实现；验证副作用必须在既有授权内 |

按第 2.1 节确认当前 `collaboration.spawn_agent` 提供选中的 `agent_type`，且支持与 `model`、`reasoning_effort`、`fork_turns` 同时使用。

默认传 `fork_turns="none"`，显式选择型号或强度时必须传该值。工具支持 `task_name` 时使用稳定短名，并填齐必需参数。用 `message` 交付[协调规则规定的派发内容](../../core/coordination-contract.md#3-派发等待取消与单写入者)、实际允许的能力及副作用、必要的未落盘用户决定。有 Spec 时，提供[规格标准](../../core/artifact-protocol.md#21-spec-artifact)及相关实施内容的可读绝对路径和精确位置，要求子代理在实施前读取。消息及其引用须让子代理取得全部所需输入。

表中的三类代理模板均不固定型号和推理强度，自动选择时显式传 B 节字段。带固定设置的代理类型只用于与该设置一致的精确请求，不能用于自动回退。

按 [Codex 自定义代理文档](https://learn.chatgpt.com/docs/agent-configuration/subagents#custom-agents)，Codex 先分别从创建请求中的显式参数、`[agents]` 默认值、父任务设置中为模型和推理强度取第一个有值的设置。如果模型由创建参数或 `[agents]` 默认值选定，而这两处都没指定强度，就用所选模型的默认强度。最后应用自定义代理文件，只覆盖该文件明确设置的 `model` 或 `model_reasoning_effort`。文件只设置模型时，保留上一步确定的强度。当前会话的参数支持与实际采用的设置分别按第 2.1 节和第 4 节核对。

工作单元需要按项目接入配置加载技能时，按以下步骤处理。

1. 确认唯一的规范技能及适用加载策略。策略不允许当前步骤读取时停止。
2. 从当前会话的技能目录取得唯一可见、可读的 `SKILL.md` 绝对路径，完整读取并核对角色、依赖、能力和副作用。版本以目录实际指向的文件为准。
3. 在 `message` 中提供技能身份、路径和允许的能力，要求子代理在行动前读取原文。必需插件或工具在子代理会话不可达时停止，不能省略技能另派任务。
4. 只有 `collaboration.spawn_agent` 本身支持结构化技能输入时才传相应字段。其余情况用完整的 `message` 交付技能输入。

### 3.1 错误与恢复

接口、必需参数、能力类型、型号或强度不受支持，或无法确认所需组合时，报告具体缺口及已有原始错误。停止受影响的调用，保留独立且已授权的工作。子代理派发不得自动改用旧协作接口、通用代理、其他接口、型号或强度。

创建已提交但尚在排队、启动或结果未知，或调用忙碌、超时、失败、取消时，保留已有的原生标识、原调用和证据，先核对实际状态。能继续时，用原标识和对应工具恢复。缺少原标识或可核实状态时，说明恢复条件，只暂停依赖部分，不自动重放或创建替代目标。用户有新的明确选择，或原目标的前提发生可证明的变化时，重新核对受影响的范围、授权、写入者和独立性，再按各入口的继续条件处理。

### 3.2 Antigravity ACP

#### 确认外部 Agent 可用

[setup-agents](../../skills/setup-agents/SKILL.md) 确认 `agy` 能找到受管角色并完成 ACP 握手后，保存连接和认证选择。缺少连接或认证方式时，客户端返回 `not_configured`，主任务按[失败处理](#调用失败或中断时)继续。

派发 Gemini 前，主任务确认本次允许的外部调用、费用和资料范围。沿用已核实角色来源和工具权限的工作目录。项目有同名角色或目录内资料超出授权时，改用只提供获准资料的隔离目录。使用已保存的连接直接调用，握手随本次调用完成。

#### 调用和续接

主任务按[协调规则](../../core/coordination-contract.md#3-派发等待取消与单写入者)核对派发条件，沿用已确认的模型安排。规划用 GPT，实施按[原生选型规则](#3-子代理类型模型与推理强度)处理。

**探索。** 自动选型时，脑暴优先用 Gemini，普通调查优先用 GPT。安排 Gemini 时，把当前问题和授权范围交给 `sacha-explorer`。重要方案质询先让 GPT 和 Gemini 各自核对。收到 `completed` 后，主任务核对事实依据。质询时按 [Explore](../../skills/explore/SKILL.md#工作与交付) 互转会改变结论的观点，判断哪些分歧还需核对，哪些取舍要交给用户。

**评审。** [工作流](../../core/workflow-contract.md#3-角色职责和启动条件)要求独立方案评审或 L1 结果评审时，优先派 Gemini 的 `sacha-reviewer`。L2 分别派独立的 Gemini 和 GPT Reviewer 审查同一基线。Gemini 评审默认用 Neon Mid，传 `--set-config model=gemini-4-neon --set-config thought_level=medium`。用户指定型号或推理级别时，按指定值请求。

主任务按[评审取证规则](../../core/assurance-contract.md#1-范围)提供目录和文件清单，并附评审基线、证据入口和适用规则。方案评审附[方案评审条文](../../core/assurance-contract.md#11-方案评审)和[结论取值](../../core/assurance-contract.md#3-评审结论与后续处理)。

收到 `completed` 后，主任务核对 Reviewer 的结论和直接证据。方案评审按[工作流](../../core/workflow-contract.md#4-生命周期与-human-路由)决定能否交用户审阅，结果评审按[验收规则](../../core/assurance-contract.md#3-评审结论与后续处理)处理。L2 交付前核对两份结果是否都覆盖最终基线。

Gemini 额度只够部分工作时，优先安排重要方案质询、方案评审和高风险结果评审。

两类任务共用同一个调用入口。主任务将任务材料和获准读取的引用写入 UTF-8 输入文件，传当前插件内 [ACP 客户端](scripts/agy_acp.py)的绝对路径。

```text
python -B <agy_acp.py> --cwd <绝对目录> --agent <角色名> --prompt-file <UTF-8 输入路径>
```

只需确认会话或查看可选配置时，省略 `--prompt-file`。返回 `session_ready` 表示会话已打开，`config_options` 给出可选值。需要指定模型或推理级别时，用 `--set-config <选项ID>=<值>`，两项都要指定时先选模型，以服务端确认的值为准。续接时有明确选型要求，也传入相应选项。

将用于展示正文或续接的原始 ACP 回执以 UTF-8 JSON 保存到任务记录。下次符合[续接条件](../../core/coordination-contract.md#2-评估拆分依赖与就绪判定)时，沿用原工作目录和角色，传入 `--resume-result <上一次成功返回的 JSON>`。已经发送过任务时，只提供新增问题、决定或改动。

#### 调用失败或中断时

- 使用 `cached-login` 时，如果返回 `Authentication required`，请用户在官方 `agy` 恢复登录，之后沿用原配置。服务端无法确认指定的模型或推理级别时，停止发送任务。客户端拒绝或取消权限请求，对不支持的回调返回错误，并记录在 `requests` 中。Gemini 在回复中提出需要副作用的验证时，由主任务按原授权处理。
- 自动选型只需一路结果时，未启用 Gemini、尚未获准外发或客户端返回 `not_configured`，直接走原生路径。`agy` 进程已经启动后，改派须有替代授权、确认不可用或额度不足的直接错误，以及原进程退出的证据。保留原标识、错误和替代结果。明确指定 Gemini 却无法完成，或 L2 缺少一路时，暂停依赖该结果的方案审阅或验收，说明已完成的部分及恢复条件。等原安排满足或用户明确调整后再继续。方案质询只取得一种模型的意见时，按实际取得的意见交付。
- 需要限定等待时间时，传 `--timeout <秒>`，外层命令另留出取消和进程回收的时间。需要主动取消时，在原命令会话发送 Ctrl+C，再核对 `turn_state`、`stop_reason`、`process_exit_code` 和相关工具是否实际停止。超时、断线或状态不明时，保留已有输出和会话标识，先核实回合终态和进程状态。证据不足时，按[第 3.1 节](#31-错误与恢复)只暂停依赖该结果的工作。

## 4. 进度与证据边界

文件变更按[工作记录规则](../../core/artifact-protocol.md#2-渐进且最小)核对，按[交互规则](../../core/human-interaction-contract.md#2-信息顺序与可见性)交付。会话提供变更登记工具时，先核对 MCP 写入、外部生成和二进制文件的支持情况，再以变更页实际收录为准。二进制登记使用宿主支持的入口，禁止转换成文本补丁代替登记。

回传 Codex 原生标识、直接父子关系、协作接口和命名空间，以及请求的 `agent_type`、型号和推理强度。自动选择时给出实际决定选型的任务类型、难度或上下文需求等直接证据。结果附上实际启动、完成、回合中断、相关写入状态、工具错误及可核对的结果引用。

保存支撑交付结论或恢复所需的工具声明、目录发现和原始调用记录。批量调用涉及多项目标时按项保留结果或引用。原始记录可访问时直接引用。

主任务收到 Gemini 的探索或评审回复后，核对并立即在主会话发一条进度，展示本次回复的关键意见。初评和每次复评分别发进度。评审时一并给出 Gemini 的评审结论。在同一条进度中附上本次 ACP 调用的原始结果 JSON 链接，供查看完整正文。ACP 会话 ID（`sessionId`）仅在首次展示或有变化时一并列出。

`spawn_agent` 的成功回执只证明工具接受参数并创建了代理。实际模型、推理强度、权限配置、功能与技能限制、工具可用性和执行行为，分别以对应的运行遥测、配置回读、工具声明或调用记录核对。配置文件、参数接受和代理自报各自只证明其覆盖的范围。

单层派发须用宿主原始调用核对父任务、会话标识、派发深度和子任务调用记录。运行行为以对应会话的直接证据为准。宿主未提供必需记录时，说明具体缺口。
