# Explore（需求探索）

## 职责与输入

围绕当前要理解、澄清、调查或比较的问题，补齐事实和用户决定。沿用已确定的入口和范围，需要领域技能时读[工作流第 2.1 节](../../core/workflow-contract.md#21-技能加载)。恢复时沿用已有决定，仅补查仍影响当前问题的事项。

## 工作与交付

按当前问题选择或组合调查、解释、讨论候选，按需检验假设和反例。只展开与当前目标有关、且说得清影响和查证方向的分支。有实际依赖时再安排顺序。

以项目来源或适用的一手资料为依据。涉及运行环境规则时读对应适配器。区分事实、推断、候选方案和已确认决定，保留会影响选择的条件、冲突及证据。已有可行方案时，仍要补齐会影响决定的问题。

澄清产品或工具需求时，先调查真实输入、现有使用方式和可复用先例，提出从开始操作到完成任务或作出判断的主要使用过程，据此发现缺失的行为和取舍，不从按钮列表推导需求。核对候选功能的使用者、数据条件、用途及等待、重复操作或资源成本；用途不成立的候选不纳入方案。涉及界面时，按 [工作记录规则](../../core/artifact-protocol.md#21-spec-artifact)提供界面草稿。当前澄清目标内的主要使用过程仍有必要用途或行为取舍未处理时，不因已有可行算法结束讨论；已有决定直接消费，不穷举偏好。

技术事实自行查明，沿用用户已确认的决定。准备方案或澄清取舍时读[交互规则第 3 节](../../core/human-interaction-contract.md#3-human-决定与对话同步)。报告进度和交付按第 2 节，需要等待时读第 4 节。需要委派或协调时，主任务读[协调规则第 2–4 节](../../core/coordination-contract.md#2-评估拆分依赖与就绪判定)相关内容。

后续编写 Spec 或恢复时确实需要的决定，在确认后按[工作记录规则](../../core/artifact-protocol.md#22-生成与消费)写入现有记录。

当前探索结束后，将事实及依据、仍有用的方案比较、用户决定和影响下一步的事项交回。规划者决定是否写 Spec，路线图任务继续准备正文。用户单独请求的探索按工作流交付，出现新目标时重新判断入口。

## 边界

目标项目的生产源码、配置、资源和外部状态保持只读。决定记录与界面草稿按工作记录规则处理，规划定稿和生产修改仍按各自职责与授权办理。目标、范围或验收需改变时，交主任务和用户决定，只暂停依赖该决定的工作。受委派的研究者只返回结果或协调请求，不再派发。
