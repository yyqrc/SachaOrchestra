# 工作记录规则

## 1. 范围与权威

本文件统一规定何时需要工作记录、最少写什么、依据发生冲突时以什么为准，以及如何完成 Spec 和恢复工作。工作记录及交接信息的定义见[术语定义](terminology-contract.md)。入口、角色和各步骤的启动条件由[入口规则](intake-contract.md)与[工作流规则](workflow-contract.md)规定。用户交互、评审和结果返回分别遵循[交互规则](human-interaction-contract.md)、[验收规则](assurance-contract.md)和[协调规则](coordination-contract.md)。

保存路径由项目接入配置或适配器决定，记录的含义、字段和依据的优先关系保持原样。通过实际文件、外部状态、文件差异（diff）和命令原始输出核实实现和验证事实。工作记录保存使用方需要的信息，或提供定位原始证据的引用。

报告或代理自报只用于定位原始证据。与原始事实冲突时，以原始事实为准并记录冲突。改变已批准的范围必须修订 Spec 并取得所需授权，不能由报告静默覆盖。

## 2. 渐进且最小

| Artifact | 生成条件 | 最小内容 |
| --- | --- | --- |
| 最终任务记录 | 同一上下文简单完成 | 修改、验证、失败/未验证与剩余风险 |
| 探索决定记录 | Spec 形成前已有确定决定供规划消费，或多轮/分支/压缩恢复需要保留探索锚点 | 已确认决定、依据/约束、未决项与 reference；恢复确需时增加原始问题、当前关注点、暂存思路，以及尚未探索/解决的实质分支、依赖与关键排除依据；疑似跨任务术语按需记录定义、排除含义、证据、边界、任务外消费者和 `Unknown` |
| Spec Artifact | 需要持久保存工作范围、提交方案批准，或为破坏性变更、跨上下文恢复提供实施规格 | 目标项目的实施规格，内容格式见第 2.1 节 |
| Execution Report | 续跑、证据索引或正式 Review | 实际变更（`delta`）、验证、偏差、风险、reference、恢复入口 |
| Review Artifact | 正式评审 | 问题、评审结论、证据缺口、下一步由谁处理 |

实施者在写入前确认目标范围内已有文件的状态。通过脚本、生成器、MCP 或其他工具间接写入时，从工具说明、领域技能、引用文档或工具实现查明会写到哪里、可能产生哪些副作用，以及如何取得完整的变更信息。已有信息仍适用于当前工具版本时直接沿用，缺少依据时再补读。工具无法提供完整信息时，执行前确定要核对的输出文件或有界目录并记录其现状，执行后用文件状态或版本控制差异核对实际输出。直接改过的脚本或工具入口只能证明其自身的变化。仍无法核实时，报告具体缺口，不猜测接口或字段。

每次写入保留来源及可取得的文件变更信息；一组相关修改完成、发生失败或超时，以及交接或交付前，核对实际新增、修改、删除和重命名，已核对且未变化的结果直接复用。已修改文件上继续产生的本次增量仍须收录，并与既有改动区分；重命名保留新旧路径，未改变的输出、备份和临时文件不混入正式改动。临时辅助脚本属于写入来源，其修改目标仍须单独核对；脚本本身确属交付物时才列入正式改动。回执缺失、截断、写入状态未知或出现范围外变化时及时核对并保留具体缺口；预期输出、样例或宿主文件卡片不能证明清单完整。

最终任务记录和 Execution Report 按上述核对结果列出实际改动。交接时随既有记录传递文件路径、变更类型、写入来源和必要证据。没有后续使用方需要持久记录时，在当前交付中说明这些内容。不得为收集文件另建任务状态，也不强制生成报告。向用户展示时遵循[交互规则](human-interaction-contract.md#2-信息顺序与可见性)。

### 2.1 Spec Artifact

Spec Artifact 供目标项目的用户、Executor 和 Reviewer 使用。Planner 必须在规划阶段完成本次实施所需的设计，将需求、澄清结果和技术决定写成精确的修改说明。接手者凭 Spec、项目规则和明确引用的项目资料即可实施，无须补设计、比较方案或猜测意图。设计范围遵循[工作流规则的运行原则](workflow-contract.md#2-运行原则)。用这同一标准核对能否交接、执行以及输入是否齐备，无须分别设置检查。规格的技术含义在 Sacha 会话之外也应清楚。

持久 Spec 使用任务目录内唯一的 `spec.md`，头部保留唯一的 `状态：<当前状态>` 行，可使用 Markdown 引用前缀。新 Spec 的状态行只使用“待批准”“已批准”或“已完成”。交付审阅时用“待批准”。已有有效批准、允许写入且尚未完成时用“已批准”。达到第 3 节的完成条件时，原位改为“已完成”。状态文字本身不授予写入或实施权限，也不证明批准或完成。已有历史文件沿用原状，恢复时凭实际批准和完成证据核对。

项目已有实施规格格式且能完整承载下表语义时沿用项目格式；否则按以下顺序生成，必需内容不得省略，按需内容为空时不保留标题：

| 顺序 | 内容 | 要求 |
| --- | --- | --- |
| 1 | 目标与范围 | 必需；说明项目问题、预期结果、本次包含的变化、必须保留的行为和已明确排除的做法及适用条件；不能只列文件或模块 |
| 2 | 共同前提与决定 | 按需；只保存多个实施步骤共同依赖的环境、数据、接口约定及关键技术取舍与理由；局部事实、前提和决定写入对应步骤 |
| 3 | 精确实施方案 | 必需。按执行顺序写清必要改动和结果。指明文件和能定位修改位置的代码符号，行号只在确有帮助时补充。字段、函数签名、参数来源、调用顺序、输入输出和复用位置等，只写会影响实施的部分。非代码修改给出精确目标和操作内容 |
| 4 | 验收 | 必需；独立说明最终可观察的项目结果及明确检查方法，覆盖预期改变、受影响的保留行为与禁止副作用；保留特殊验证要求的依据，不复述实施步骤或写入工作流执行分类 |
| 5 | 未解决问题与验证限制 | 按需；只记录当前确实存在的未知、具体影响与验证方式或限制。必须补充设计才能实施的问题未解决前不得交付执行；尚需运行验证不等于设计缺失，不自动扩展方案 |

涉及用户操作或结果呈现时，以代表性输入下从开始操作到完成任务或作出判断的主要使用过程组织必要行为，就近写入精确实施方案，并与技术实现及验收对应：

- 入口由实际用途和数据条件决定，写清输入由谁产生、是否足够支撑操作及结果解释。区分日常操作、开发验证和数据生产职责；不能因底层能力存在就自动增加用户入口。
- 对会改变结果的关键操作，确定操作前提、默认状态、改变的数据、同步更新的显示与统计、保留的选择或视野，以及本次涉及的重算、缓存与失效条件。连续比较哪些结果、如何隔离处理因素，先由使用目标确定，再依据真实输入规模选择计算与资源方案。
- 显示内容须对应真实数据含义：按任务说明选择对象、编号粒度和关联关系、图层与图例含义；参数经目标数据、处理结果到显示和统计的关系必须一致。可视化仅模拟或只改变显示时明确区分，不能把显示近似当成处理数据。

涉及新界面或主要交互变化时，在冻结技术实施方案前提供[界面草稿](terminology-contract.md)，优先用轻量 HTML 模拟布局、控件和默认内容。草稿须能演示需要决定的关键操作及状态变化，使用有区分度的代表性或明确标示的模拟数据，不以空框、无响应按钮或始终相同的结果代替行为设计；简单调整可用局部示意，已有设计足够时直接复用。Planner/Explore 先自行走通拟演示操作，再交 Human 修正用途与取舍；不提前实现完整算法或产品。独立草稿的本地生成与预览属于规划材料，不授权生产接入、部署或外部服务。

必要决定及理由进入相应实施单元。草稿仍被后续消费时，随既有任务材料保存，Spec 明确引用其适用部分；发生冲突先修订，不让执行者猜测。验收沿同一主要使用过程给出可观察结果，覆盖明确要求和跨区域、跨阶段联动，而非只检查功能分别存在。只设计本次实际涉及的行为，不穷举状态或增加逐控件批准；生产证据范围遵循验收规则。

局部事实、技术决定及理由只在相应修改单元完整说明一次；跨步骤共用的定义放入共同前提与决定，其他位置引用。已确认的停用、清理、兼容或回退要求进入相关步骤，其结果要求进入验收，不再单列默认章节。代码与资源位置随步骤给出；长文档可提供仅含链接的导航，不重复建立位置、函数、参数及步骤清单。已解决问题的依据就近保留，不再列入未解决问题。

Planner 先从项目规则、源码、配置、正式文档或已确认的项目决定核实项目事实和现有定义。代码、字段、配置、资源和正式术语沿用项目来源中的精确名称。简称和别名也须有项目来源。其他资料可作线索，不能单独定义项目约束或术语。

为新增标识或概念命名时，写清定义、直接使用方和适用边界，按上述项目来源核对目标位置、相邻负责方和命名习惯。Sacha 的角色、各步骤的启动条件和临时分析用语只用于本任务编排。不得据此给项目概念或实现命名，按名称的来源和含义判断。

转述项目约束、验收或失败保护时，保留主体、条件、动作、规范强度、边界和例外。项目来源没有的概括性标签不得扩大或替代原意。

Planner 根据已核实的事实和需求完成必要设计，将新提议标为待批准的技术决定，随 Spec 提交审阅。

按材料在当前任务中的用途判断来源。Execution Report、Review Artifact、Handoff、自报和内部推理只提供线索或证据索引。Sacha 规则、技能和适配器本身是目标项目的现行产品源码或规范时，可作为该产品接口、约束和拟改行为的依据。混合材料只提取有项目来源支持的内容。

Spec 只记录项目行为、设计和验收。项目运行所需的环境和数据前提按作用范围写入共同前提或相应实施步骤。当前任务的角色、流转、协调、授权、单一写入者、验收分工、裁决、迁移与恢复、宿主传输由对应规则处理。需要交接或恢复时随既有记录或消息交付必要信息，其余留在当前任务。

Spec 必须确定本次实际涉及且实施所需的算法、接口、数据结构、调用链、结果映射和失败时的行为。异常或恢复设计继续遵循工作流规则对必要性的限制。执行者遇到局部出入时，先按实际代码核对并解决，例如函数挪了位置、辅助函数已有等价实现。只要保持已批准的关键技术决定、对外行为、接口、数据含义、工作范围、授权和验收，执行者可以自行调整局部做法并验证。确需补齐缺失的设计、改变这些约束，或证据不足以判断能否安全继续时，把具体位置、事实和证据交回主任务。只暂停依赖该问题的工作。

批准后的 Spec 是实施与评审基线；Human 最新明确决定优先于冲突旧条款。决定变化时原位替换受影响的范围、方案和验收，并核对依赖同一前提的现行记录，不只在旧要求前追加一条新说明。实施事实证明范围、技术决定或验收失效时，Executor 返回事实和证据，由工作流规则决定下一路由；Spec 不保存角色或路由指令。

需求边界及必要理由写入上述对应内容，不另建同义清单或要求固定三段格式。没有已确认的排除项时不编造禁止事项；已有决定足以设计时不为填写格式重复提问。必要决定必须写入 Spec，项目引用必须明确可达，不能仅由聊天、会话摘要或不可达记录承载。

已有改动、验证结果和剩余工作等当前执行状态由既有 Execution Report 或恢复记录承载，接手所必需的记录须提供明确可达的 reference。

### 2.2 生成与消费

工作记录只在有使用方时创建。探索决定优先写进项目已有的记录。项目没有约定且后续规划或恢复需要这些决定时，使用任务目录中的 `decisions.md`。内容限于第 2 节表中所列事项。旧项确认或失效后，在原记录中精简。

Explore 或 Planner 为任务恢复或 Spec 写决定记录时，项目概念和拟议实现名称同样遵循第 2.1 节的来源和命名要求。

Planner 读取决定记录形成 Spec 并沿用已确认术语。项目上下文候选在收尾时基于最终实现/Review 证据复核，并在文档授权覆盖后进入项目 `CONTEXT.md`。

一个事实只写一次。Spec 按第 2.1 节保存项目内容。工作流中的目标、范围、验收与交接信息引用 Spec 对应位置。Review Artifact 引用 Baseline、Execution Report 与原始证据，不得另行定义 `delta`。按[交互规则](human-interaction-contract.md#2-信息顺序与可见性)向用户直接交付审阅重点和本轮最终建议。
长度按风险和恢复需要自适应，不为格式拆文件。各 Artifact 的失败、未验证、授权、风险、证据与进入条件只由其直接消费者和本协议的内容边界决定，不得因压缩丢失，也不得为形式完整复制到无消费者的 Artifact。

Execution Report 保存在 Spec 或任务约定的 Artifact 位置。收尾时的项目文档由[工作流规则](workflow-contract.md#6-项目文档)与 [`document-project`](../skills/document-project/SKILL.md)处理候选和授权，目标位置由 Project Integration 决定。

## 3. Spec 完成

- 工作流要求完成 Spec 时，主任务从当前任务、已批准 Spec 的引用或用户明确给出的 `path` 定位当前 Spec。不得扫描 Spec 存储目录，按日期或名称猜测本任务的规格。
- 确认当前 Spec 是唯一、可访问且已批准的 `spec.md`，并且头部只有一条状态行。任一条件不满足时，预检失败，保留原状态。
- 主任务符合[“已完成”的条件](coordination-contract.md#6-完成返回与偏差)，且必需验证与适用评审已核对并满足要求时，才可把 Spec 标为已完成。条件不足时，保留原状态并说明缺口。
- 条件均满足且状态行已是“已完成”时，直接返回 `no_op`。
- 状态行需要更新且已有写入授权时，用带并发检查的局部编辑原位改为“已完成”，然后回读验证。保留路径、文件名、其余正文和工作记录身份。不得用整文件替换覆盖其他并发编辑。
- 已授权的编辑失败时，先核对实际文件状态。确认目标和原内容未变、失败只由文件自身的只读属性引起时，临时解除该属性，按原有并发保护重试一次。尝试结束后，在原文件或本次已确认写入的版本上恢复该属性。用户明确要求只读、目录权限及运行环境限制继续适用。重试或恢复属性失败时，报告实际状态和恢复条件。
- 其余失败保留原始错误和实际状态。不得盲目重试、移动文件或创建替代工作记录。
- Spec 完成依据已核实的主任务结果。项目文档仍由 `document-project` 按其策略和授权独立处理。

## 4. Handoff

正式跨角色交接或恢复工作时，只有接收方凭现有范围、工作记录和运行环境传递的信息无法安全继续，才补写 Handoff。按需提供以下信息。

- 路由标识：稳定的 任务或范围修订号，以及 Source/Target/Owner 中传输未携带但消歧必需的部分；
- 结果：已完成且可核实的结果；
- 范围：批准 Spec/用户目标的 reference；
- 产物/证据：恢复材料与真实状态 reference；
- 风险/进入条件：偏离、未验证、风险及开始前必须满足的授权、状态和验证。

名称、顺序和载体由消费者决定；空内容省略。Human 可见内容遵循交互规则。确有领域或 Runtime 消费方时可增加带命名空间的扩展；扩展沿用本协议的权威与授权边界。

## 5. 恢复规则

- 把交接信息写进已有工作记录或消息，不单建 Handoff 文件。
- 引用须稳定、可达。可移植的工作记录优先使用相对位置或不依赖环境的标识。
- 同一环境内恢复确需绝对路径时，标记 `non-portable`，有相对位置或与环境无关的引用时一并提供。运行环境实例 ID、模型、界面状态和内部存储标识，仅随运行环境内部的消息传递。
- 评审结论、报告或代理自报不能替代引用所指向的原始证据。
- 返修/重规划保持 Task ID，除非 Human 建立新范围。
- 接手方核对可用的流转标识、范围、工作记录、证据和进入条件。条件不足时暂停或报告部分完成。
- 恢复时沿用既有 Spec、Execution Report 和评审结果，分别恢复已批准的要求、执行状态和正式裁决。记录与实际状态不一致时，按本协议第 1 节核对原始证据。
- 从 Spec 恢复预期改变、保留行为、排除做法及其适用条件和必要理由，再核对当前实现与证据；上下文压缩、交接或会话切换不使这些约束失效，不得只按进度摘要重新选回已排除的方案。
