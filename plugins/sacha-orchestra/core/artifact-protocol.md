# Artifact Protocol（产物协议）

> 状态：规范性 Core 合同

## 1. 范围与权威

本文是 Artifact 生成条件、最小内容、权威关系、Spec 完成和恢复规则的唯一权威。Artifact、Spec Artifact、Spec 完成、探索决定记录、Execution Report、Review Artifact 与 Handoff 的定义见[术语合同](terminology-contract.md)；入口/Role/Gate 由 [Intake Contract](intake-contract.md) 与 [Workflow Contract](workflow-contract.md) 定义，Human 可见交互由 [Human Interaction Contract](human-interaction-contract.md) 定义。
Review 与返回分别由 [Assurance Contract](assurance-contract.md)、[Coordination Contract](coordination-contract.md) 定义。

保存路径由 Project Integration/Adapter 决定，不改变语义、字段或权威。真实文件、外部状态、文件差异（diff）和命令原始输出仍是实现与验证事实；Artifact 只索引或承载消费者需要的信息。

报告与原始事实冲突时以原始事实为准并记录冲突。改变批准 Scope 必须修订 Spec 并取得所需授权，不能由报告静默覆盖。

## 2. 渐进且最小

| Artifact | 生成条件 | 最小内容 |
| --- | --- | --- |
| 最终任务记录 | 同一上下文简单完成 | 修改、验证、失败/未验证与剩余风险 |
| 探索决定记录 | Spec 形成前已有确定决定供规划消费，或多轮/分支/压缩恢复需要保留探索锚点 | 已确认决定、依据/约束、未决项与 reference；恢复确需时增加原始问题、当前关注点、暂存思路，以及尚未探索/解决的实质分支、依赖与关键排除依据；疑似跨任务术语按需记录定义、排除含义、证据、边界、任务外消费者和 `Unknown` |
| Spec Artifact | 持久 Scope、批准方案或跨上下文恢复 | 目标项目实施规格；内容格式见第 2.1 节 |
| Execution Report | 续跑、证据索引或正式 Review | 实际变更（`delta`）、验证、偏差、风险、reference、恢复入口 |
| Review Artifact | 正式 Review | 问题、裁决结果（Outcome）、证据缺口、下一路由 |

### 2.1 Spec Artifact

Spec Artifact 面向目标项目的 Human、Executor 和 Reviewer。必须在规划阶段完成本次实施所需的必要设计，将需求、澄清结果和技术决定落实为精确的修改说明，使执行者依据 Spec、项目规则及明确引用的项目资料，无需补充设计、比较方案或猜测意图即可实施。设计范围遵循 [Workflow Contract 的运行原则](workflow-contract.md#2-运行原则)。这一标准统一覆盖可交接、可执行与自包含，不另设并列检查；规格的技术含义不依赖 Sacha 上下文。

持久 Spec 使用任务目录内唯一的 `spec.md`，头部保留唯一的 `状态：<当前状态>` 行，可使用 Markdown 引用前缀；完成时按第 3 节原位修改为“已完成”。初次交付待批准时标记“待批准”，已有批准时按实际状态填写；状态文字本身不替代批准事实或完成证据。

项目已有实施规格格式且能完整承载下表语义时沿用项目格式；否则按以下顺序生成，必需内容不得省略，按需内容为空时不保留标题：

| 顺序 | 内容 | 要求 |
| --- | --- | --- |
| 1 | 目标与范围 | 必需；说明项目问题、预期结果、本次包含的变化、必须保留的行为和已明确排除的做法及适用条件；不能只列文件或模块 |
| 2 | 共同前提与决定 | 按需；只保存多个实施步骤共同依赖的环境、数据、接口约定及关键技术取舍与理由；局部事实、前提和决定写入对应步骤 |
| 3 | 精确实施方案 | 必需；按执行顺序组织必要修改及完成结果。每个修改单元就近写清文件、当前行号与稳定代码锚点、新增或修改的字段和函数签名、参数来源、调用顺序、输入输出、必要转换、现有实现的复用位置与接入方式，以及影响实施的局部依据和检查方法。只写实际涉及内容，不为填满格式新增函数或机制；非代码修改给出对应的精确目标和操作内容 |
| 4 | 验收 | 必需；独立说明最终可观察的项目结果及明确检查方法，覆盖预期改变、受影响的保留行为与禁止副作用；保留特殊验证要求的依据，不复述实施步骤或写入工作流执行分类 |
| 5 | 未解决问题与验证限制 | 按需；只记录当前确实存在的未知、具体影响与验证方式或限制。必须补充设计才能实施的问题未解决前不得交付执行；尚需运行验证不等于设计缺失，不自动扩展方案 |

涉及用户操作或结果呈现时，以代表性输入下从开始操作到完成任务或作出判断的主要使用过程组织必要行为，就近写入精确实施方案，并与技术实现及验收对应：

- 入口由实际用途和数据条件决定，写清输入由谁产生、是否足够支撑操作及结果解释。区分日常操作、开发验证和数据生产职责；不能因底层能力存在就自动增加用户入口。
- 对会改变结果的关键操作，确定操作前提、默认状态、改变的数据、同步更新的显示与统计、保留的选择或视野，以及本次涉及的重算、缓存与失效条件。连续比较哪些结果、如何隔离处理因素，先由使用目标确定，再依据真实输入规模选择计算与资源方案。
- 显示内容须对应真实数据含义：按任务说明选择对象、编号粒度和关联关系、图层与图例含义；参数经目标数据、处理结果到显示和统计的关系必须一致。可视化仅模拟或只改变显示时明确区分，不能把显示近似当成处理数据。

涉及新界面或主要交互变化时，在冻结技术实施方案前提供[界面草稿](terminology-contract.md)，优先用轻量 HTML 模拟布局、控件和默认内容。草稿须能演示需要决定的关键操作及状态变化，使用有区分度的代表性或明确标示的模拟数据，不以空框、无响应按钮或始终相同的结果代替行为设计；简单调整可用局部示意，已有设计足够时直接复用。Planner/Explore 先自行走通拟演示操作，再交 Human 修正用途与取舍；不提前实现完整算法或产品。独立草稿的本地生成与预览属于规划材料，不授权生产接入、部署或外部服务。

必要决定及理由进入相应实施单元。草稿仍被后续消费时，随既有任务材料保存，Spec 明确引用其适用部分；发生冲突先修订，不让执行者猜测。验收沿同一主要使用过程给出可观察结果，覆盖明确要求和跨区域、跨阶段联动，而非只检查功能分别存在。只设计本次实际涉及的行为，不穷举状态或增加逐控件批准；生产证据范围遵循 Assurance Contract。

局部事实、技术决定及理由只在相应修改单元完整说明一次；跨步骤共用的定义放入共同前提与决定，其他位置引用。已确认的停用、清理、兼容或回退要求进入相关步骤，其结果要求进入验收，不再单列默认章节。代码与资源位置随步骤给出；长文档可提供仅含链接的导航，不重复建立位置、函数、参数及步骤清单。已解决问题的依据就近保留，不再列入未解决问题。

Planner → 写入既有项目概念 → 沿用项目当前定义。

Planner → 写入既有代码、字段、配置、资源或正式项目术语 → 使用项目来源中的精确名称 → 项目来源未定义简称或别名时不得自行新增。

Planner → 写入新增实现标识或项目概念 → 按项目语义说明定义、直接消费者和边界，并核对目标位置、相邻 Owner 与项目当前命名习惯 → 命名依据和含义只接受项目规则、源码、配置、正式项目文档或已确认项目决定，不得把 Sacha/Agent 的 Role、Gate、工作意图、内部推理或其他临时规划抽象作为项目命名依据。语言、单词或命名形式本身不决定是否合法。

Planner → 改写项目约束、验收或失败保护 → 保留项目来源中的主体、条件、动作、规范强度、边界与例外 → 不得用项目来源没有的概括性标签扩大或替代原意。

Planner → 确定 Spec 中的已有事实 → 只接受项目规则、源码、配置、正式项目文档或已确认项目决定 → 其他来源不得单独定义项目约束或项目术语。必要的新设计由 Planner 根据这些事实与需求作出，明确标为拟议技术决定并随 Spec 提交审阅批准。

按内容在当前任务中的用途判断来源：Execution Report、Review Artifact、Handoff、自报和内部推理只提供线索或证据索引，不能单独定义项目事实。Sacha Core 合同、Skill 或 Runtime Adapter 本身是目标项目的现行产品源码或规范时，可用于描述该产品的接口、约束和拟修改行为；当前任务如何被编排、派发和传输仍不进入 Spec。混合输入只提取有项目来源支持的内容。

Planner → 遇到用于编排当前任务的角色、路由、协调、验证责任分类、迁移、裁决或运行时传输信息 → 分别交给 [Workflow Contract](workflow-contract.md)、[Assurance Contract](assurance-contract.md)、[Coordination Contract](coordination-contract.md)、Review Artifact、Handoff 或 Runtime Adapter → 不写入 Spec。

项目运行所需环境和数据前提按作用范围进入“共同前提与决定”或对应实施步骤；当前任务的授权、任务迁移、单写入者和恢复路由由主任务按 [Intake Contract](intake-contract.md)、[Workflow Contract](workflow-contract.md) 与 [Coordination Contract](coordination-contract.md) 判断，并在存在恢复消费者时通过 Handoff 交付，不写入 Spec。

Spec 必须确定本次必要的算法、接口、数据结构、调用链、结果映射和失败语义；只确定本次实际涉及的内容，异常或恢复设计仍受 Workflow Contract 的必要性条件约束。执行者可自主处理的仅是不改变规格含义的机械适配，如局部变量命名、遵循周边格式及插入后行号变化；不得以“局部实现”代替未完成的设计。遇到规格缺失、矛盾、现场不符，或需要改变方案才能解决的问题时，执行者交回具体位置、事实和失败证据，由主任务分析并按 Workflow Contract 调整；只暂停依赖该问题的工作，不自行补设计、替换技术路线或扩大范围。

批准后的 Spec 是实施与评审基线；Human 最新明确决定优先于冲突旧条款。决定变化时原位替换受影响的范围、方案和验收，并核对依赖同一前提的现行记录，不只在旧要求前追加一条新说明。实施事实证明范围、技术决定或验收失效时，Executor 返回事实和证据，由 Workflow Contract 决定下一路由；Spec 不保存角色或路由指令。

需求边界及必要理由写入上述对应内容，不另建同义清单或要求固定三段格式。没有已确认的排除项时不编造禁止事项；已有决定足以设计时不为填写格式重复提问。必要决定必须写入 Spec，项目引用必须明确可达，不能仅由聊天、会话摘要或不可达记录承载。

已有改动、验证结果和剩余工作等当前执行状态由既有 Execution Report 或恢复记录承载，接手所必需的记录须提供明确可达的 reference。

### 2.2 生成与消费

Artifact 只在存在消费者时创建。探索决定记录优先使用项目既有载体；无约定且存在规划或恢复消费者时使用任务目录中的 `decisions.md`。它只保存已确认决定、未决项、必要 reference 和压缩后必须重建的最小恢复边界，旧项确认或失效后原位压缩。

Explore 或 Planner → 写入供恢复或 Spec 消费的决定记录 → 项目概念与拟议实现标识沿用第 2.1 节的来源和命名边界；Sacha/Agent 的内部工作意图、挑战图、Role/Gate 与临时分析标签只服务各自流程消费者 → 不得写成项目概念或实现命名。

Planner 读取决定记录形成 Spec 并沿用已确认术语。项目上下文候选在收尾时基于最终实现/Review 证据复核，并在文档授权覆盖后进入项目 `CONTEXT.md`。

一个事实只写一次：Spec 保存第 2.1 节定义的项目内容；工作流中的目标、Scope、验收与 Handoff 只引用对应 Spec 内容，不复制其定义；Execution Report 的 `delta` 专指表中的实际变更，Review Artifact 不定义 `delta`，只保存问题、裁决结果（Outcome）、证据缺口和下一路由，并引用 Baseline、Execution Report 与原始证据。Human 审查关注点（Review Focus）和当轮最终建议清单按 Human Interaction Contract 直接交付。
长度按风险和恢复需要自适应，不为格式拆文件。各 Artifact 的失败、未验证、授权、风险、证据与进入条件只由其直接消费者和本协议的内容边界决定，不得因压缩丢失，也不得为形式完整复制到无消费者的 Artifact。

Execution Report 在恢复、证据索引或正式 Review 存在消费者时随任务形成，并保存到 Spec/任务约定的 Artifact 位置。Project Documentation 的候选与授权由 Workflow 收尾和 `document-project` 决定，目标位置由 Project Integration 决定；Execution Report 继续留在任务 Artifact 位置。

## 3. Spec 完成

- 主任务 → 收到 Workflow Contract 路由的 Spec 完成动作 → 从当前任务、批准 Spec reference 或 Human 明确 path 取得当前 Spec → 不得扫描 Spec storage root 按时间或名称猜测当前任务。
- 当前 Spec 缺失、存在多个候选、不是可达的单一 `spec.md`、未批准或头部状态行不唯一 → 失败关闭且不写入。
- 当前任务尚未进入 `goal_complete`，或必需验证与适用 Review 尚未满足 → 保持 Spec 原状态并报告未满足条件 → `goal_partial`、`goal_cancelled`、`goal_superseded` 和其他非完成终态不得标记为已完成。
- 当前上下文可写，且本次 Spec 状态写入由实施批准或显式收口请求覆盖 → 生成精确状态行编辑计划，再用 Runtime 的并发检查局部编辑把该行原位改为“已完成”并回读验证 → path、文件名、其余正文和 Artifact 身份保持不变；不得用整文件替换覆盖并发正文。
- Spec 已是“已完成” → 返回 `no_op`；状态行变化、只读上下文或局部编辑失败 → 不盲目重试、不移动文件、不创建替代 Artifact，报告原始缺口与恢复条件。
- Spec 完成只消费任务终态，不生成项目文档；项目文档继续由 `document-project` 按独立策略和授权处理。

## 4. Handoff

只有正式跨 Role 或恢复消费者无法从现有 Scope、Artifact 和原生传输安全继续时才写 Handoff。它按需提供：

- 路由标识：稳定的 Task/Scope 修订号，以及 Source/Target/Owner 中传输未携带但消歧必需的部分；
- 结果：已完成且可核实的结果；
- 范围：批准 Spec/用户目标的 reference；
- 产物/证据：恢复材料与真实状态 reference；
- 风险/进入条件：偏离、未验证、风险及开始前必须满足的授权、状态和验证。

名称、顺序和载体由消费者决定；空内容省略。Human 可见内容遵循 Human Interaction Contract。确有领域或 Runtime 消费方时可增加带命名空间的扩展；扩展沿用本协议的权威与授权边界。

## 5. 恢复规则

- Handoff 嵌入承载 Artifact/消息，不单建 Handoff 文件。
- reference 必须稳定、可达，可移植 Artifact 优先相对位置或环境中立标识。
- 同环境恢复确需绝对路径时标记 `non-portable`，可用时同时给出相对或环境中立 reference；Runtime 实例 ID、模型、界面状态和内部存储标识只进入仅供 Runtime 的传输。
- Outcome、报告或 Role 自报不能替代证据 reference 指向的原始证据。
- 返修/重规划保持 Task ID，除非 Human 建立新 Scope。
- Target 核对可用路由标识、Scope、Artifact/Evidence 和 Entry Condition；不满足时暂停或报告部分完成。
- 恢复继续使用 Spec、Execution Report 和 Review 作为权威状态。
- 从 Spec 恢复预期改变、保留行为、排除做法及其适用条件和必要理由，再核对当前实现与证据；上下文压缩、交接或会话切换不使这些约束失效，不得只按进度摘要重新选回已排除的方案。
- 上下文即将切换或确有后续接手者，且现有传输不足以继续时，在已有恢复载体中保留下一步需要的接口结论、适用条件、精确来源、已完成部分与剩余缺口；不只记录进度或文件列表。失效结论及时更新，不复制大段源码或另建台账。恢复后从有效结论继续，仍为修改和验证读取必要原文，不要求零重读或每步写记录。
