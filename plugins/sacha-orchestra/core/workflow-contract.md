# 工作流规则

## 1. 范围

本文统一规定角色职责、各步骤的开始与结束条件、Roadmap 在主流程之外调用哪些技能，以及如何根据用户决定继续。显式 Explore 沿用自己的窄授权。术语、入口、用户交互和评审分别见[术语定义](terminology-contract.md)、[入口规则](intake-contract.md)、[交互规则](human-interaction-contract.md)和[验收规则](assurance-contract.md)。
拆分、就绪判定、调度、取消、汇总、结果返回和迁移责任的移交见[协调规则](coordination-contract.md)，持久记录见[工作记录规则](artifact-protocol.md)。

工作流独立于平台和项目。适配器负责各运行环境的传输，项目接入配置和领域技能提供项目知识，角色技能说明对应角色的做法。按当前步骤的实际需要读取规则，后续步骤需要的规则在使用前再读。

## 2. 运行原则

- 需要正式实施角色时，由 Executor 执行。规划、协调和独立评审只有满足各自启动条件时才开展。单一写入者和共享写入的安排遵循[协调规则](coordination-contract.md#3-派发等待取消与单写入者)。
- Human 保留目标、范围、高影响动作和工作区外状态授权。
- 设计与实施必须以解决当前问题的最小改动形成方案；优先复用现有实现，迁移时只适配必要差异。Spec 的设计完整性与说明精度由 [工作记录规则](artifact-protocol.md#21-spec-artifact)统一规定。新增机制必须有当前需求或已确认可达的失败依据，并说明现有实现或局部修改为何不足；通用化必须有明确的复用需求，依据不足的扩展必须删除或收缩。
- 修复既有系统故障时，先核对设计要求的输入、处理步骤和负责方。用同条件下的正常先例定位偏离。找不到正常先例时如实说明，按设计约定和直接证据判断。
  - 先区分配置遗漏、既有步骤漏处理和机制本身有缺陷，再决定修哪里。归属仍不明确时补查证据。禁止杜撰先例或先试加兜底。
  - 能在原有负责位置补齐时，就在那里修复。扩展公共机制或新增通用兜底前，先证明按既有约定仍会失败，并说明为何局部修复不足。故障对象缺输入、有可复用工具或代码改动少，各自都不足以证明通用能力缺失。
  - 按职责和影响范围判断最小改动。验证修复结果时，仍须有证据支持缺陷归属。
- 讨论、澄清和研究允许围绕当前目标提出候选方向、待证假设与反例，比较取舍并发现新问题；探索输入不要求达到 Spec 精度。区分事实、假设、候选与已确认决定，只有已确认采用的内容才能成为需求或实施机制；探索的分支、阻塞判定与收敛遵循 [Explore](../skills/explore/SKILL.md)。
- 只有 Human 明确要求，或已有证据表明本次修改会造成具体错误时，才将边界、异常、兼容、恢复或回退的必要处理纳入方案。不得为形式完整、自包含或便于验收而穷举这些问题或新增机制、抽象及配套设施。当前讨论目的已满足、必要设计已足以落实目标时，停止扩展设计；需要交付 Spec 时须达到工作记录规则的标准。项目与领域的既有必要约束继续适用；发现需由 Human 决定的数据迁移时，说明具体影响，不默认建设迁移或恢复机制。
- 实施和验证的事实依据按[工作记录规则第 1 节](artifact-protocol.md#1-范围与权威)核对。
- 主任务负责推进整个任务，并按[协调规则第 6 节](coordination-contract.md#6-完成返回与偏差)判断本轮结束时的结果。只有主任务能运行 Manager 和派发工作。委派代理的完成结果和协调请求都是中间结果。
- 授权、Reviewer 来源独立性、单写入者、返回标识/去重、安全、Handoff 必要语义与原始证据权威不可降级。
- 默认在当前会话完成。确需为方案批准、后续使用或恢复保存信息时，按[工作记录规则第 2 节](artifact-protocol.md#2-渐进且最小)判断保存哪类记录及其最小内容。
- 所有任务沿用同一通用生命周期。处理特殊目标需要调整流程时，先向 Human 说明真实失败模式、现有路由缺口和拟议改动的影响，取得明确批准后调整通用流程。禁止新增隐藏阶段、旁路或第二套生命周期。
- 显式 Roadmap 独立处理。事实或用户决定不足时只路由 Explore，结果返回 Roadmap。自包含正文就绪后只路由 `document-project`，写入结果返回 Roadmap 后结束本次规划。后续独立 Spec 任务见第 4 节。
- 委派、交接或恢复需要时读取协调规则与适配器的对应条文。需要验收分类或工作记录时读取相应的验收或工作记录规则。

### 2.1 技能加载

本节沿用[术语定义](terminology-contract.md)对 Project Integration、规范技能和技能加载策略的定义。

- `on-demand`：当前节点的任务语义匹配规范 Skill 的 `description`，且设计、规划、调查或实施需要其约束或领域输入时加载；只读 `change-guard` 不等待项目写入授权。
- `change-authorized`：工作范围已有 Human 修改授权，且当前节点需要该 Skill 实施项目变化时加载；加载不表示可以执行 Skill 内的写入、构建、Runtime 或外部动作。
- `review-only`：当前节点是显式或本文件路由的 Reviewer，且该 Skill 会改变裁决时加载。
- `risk-matched`：当前范围、验收或已识别风险需要该 Skill 的验证输入或证据时加载；不为形式完整自动执行编译、Runtime 或其他高成本动作。
- 当前节点按 Runtime Skill catalog 的 canonical `name`、`description` 与 `path` 选择唯一匹配，依项目策略加载并完整读取正文；实际动作须满足 Role 边界、前置与授权。名称或描述不足以唯一选择时不得猜测。
- 策略不允许加载时不通过别名、包装或回退再次调用该 Skill；没有已确认策略条目时不推导策略，沿项目规则和已有授权选择可用路线。前置不足只暂停依赖部分；工具不可用时按第 4 节选择替代，不能以替代绕过原动作的限制。保留由此未完成的验证。

## 3. 角色职责和启动条件

| 角色 | 唯一责任 | 禁止 |
| --- | --- | --- |
| [Planner](../skills/planner/SKILL.md) | 调查事实、比较实质方案、确定工作范围、方案决定和验收条件 | 把规划当授权；实施生产修改 |
| [Executor](../skills/executor/SKILL.md) | 有 Spec 时按精确规格实施、核对与验证；无 Spec 时在明确目标内自主实施；记录证据 | 自行补充或替换 Spec 的必要设计；静默改变 工作范围或已确定的决定；虚报验证 |
| [Reviewer](../skills/reviewer/SKILL.md) | 以独立来源对照范围、真实状态和原始证据裁决 | 修改验收依据以求通过；默认修复 |

| 步骤 | 何时启动 | 单独出现时不足以启动 |
| --- | --- | --- |
| Planner | 会改变实施路线的目标、验收、负责边界或关键方案仍待比较与冻结；用户要求或实际后续消费者需要完整 Spec；难回退的跨 Owner 决策 | 复杂、文件多、耗时、跨插件、已明确的行为修改；可局部补齐的信息；Agent 自行提议写 Spec |
| Reviewer | 对安全、权限或持久数据边界产生实质影响；破坏性变更或困难回退；影响验收的证据冲突、关键证据缺口的阻塞性不明，或补证受阻后仍需独立裁决；Human 要求 | 仅涉及相关名称或文件；文档标签、版本封装、可回退且完整验证的局部修改；当前 Executor 可按既定验收完成的补证 |
| Manager | 实际工作单元需要统一安排依赖、并发写入或负责归属，包括恢复时重新安排这些工作 | 多个候选想法、普通顺序步骤、理论上可拆分；困难、耗时、多文件；单个有界委派 |

Executor 先在既有职责和授权内完成能做的必需验证和补证。已经明确且能处理的证据缺口直接补齐。其他独立评审条件成立、证据冲突或证据缺口是否阻塞交付尚不明确时，仍进入独立评审。必需验证实际完成后才能记为完成。

这些条件决定使用哪个角色或是否协调。已确认的做法、范围、授权和后续安排直接沿用。用户显式调用时按入口规则进入对应角色。恢复时只补齐缺失或失效的事实，范围、验收、职责、安全或依赖变动时，只重新判断受影响的步骤。直接处理的任务出现新事实时按入口规则重判。派发、写入和交付所需检查随相应动作完成。已读且仍适用的规则和技能直接沿用。单个有界委派由主任务按协调规则管理。
名称或新上下文不证明 Reviewer 独立；参与当前方案/实现者不能作独立 Reviewer。

## 4. 生命周期与 Human 路由

按[入口规则](intake-contract.md#3-入口判断)确定工作方式，按第 3 节安排所需角色。协调结束后回到原步骤，自动存档按第 6 节判断。

Planner 自行调查、完成局部澄清，并询问只有用户能作出的明确决定。需要持续探索、比较候选方案或处理相互依赖的问题时，交 Explore。必要事实和决定齐备后形成精确 Spec。实施所需设计仍有缺口时，先补齐再交付执行。外部材料按 [交互规则第 3 节](human-interaction-contract.md#3-human-决定与对话同步) 核对和确认。

用户要求调整时，返回 Planner。用户取消或表示不再继续时，主任务结束。

显式 Roadmap 按[入口授权](intake-contract.md#4-入口决定)和第 2 节单独处理。`closeout` 按第 5 节执行。显式文档请求和正常实施后的文档候选均见第 6 节。Feedback 的入口授权与目标交付分别见[入口规则](intake-contract.md#4-入口决定)和[协调规则](coordination-contract.md#6-完成返回与偏差)。

Roadmap 完成后，候选 Spec 已有明确目标、来源和后续使用方，且另开任务能实质改善澄清、保存或恢复时，才按[交互规则](human-interaction-contract.md#3-human-决定与对话同步)推荐另开规划任务。已有针对该任务的创建授权时直接沿用，否则只确认创建这项动作。适配器把明确的规划请求写入初始输入。新任务依据自身请求及[入口授权](intake-contract.md#4-入口决定)继续，路线图的状态和上下文只供核对。

### 4.1 实施批准

实际需要请求实施批准、收到实施批准或准备按已有批准实施时，读取本节。普通批准和明确迁移批准见[术语定义](terminology-contract.md)。按[入口规则第 4 节](intake-contract.md#4-入口决定)处理实施所需的决定与授权。

已授权实施且未选择迁移时，由当前主任务按范围实施。两种实施批准均覆盖第 5 节规定的 Spec 状态更新。项目文档、任务迁移、安装、Git、发布及其他外部动作各自按对应授权办理。

### 4.2 执行任务迁移

当前确有另开执行任务的需要或用户提出迁移时，读取本节。可靠迁移信号和执行任务迁移前提见[术语定义](terminology-contract.md)。只有可靠迁移信号成立且另开任务确实能改善交接或恢复时，才建议迁移。已有授权可在当前任务继续时，无须为这个建议停下。达到审阅条件时及时交付，无须为取得迁移信号而延后。

迁移须明确授权。用户选择明确迁移批准时，来源任务停止实施和写入派发，核对执行任务迁移前提。全部满足后，按适配器查询、复用或创建唯一目标。标识、去重、单一写入者和责任移交按协调规则处理。

用户已明确批准迁移，但有迁移前提未满足时，来源任务报告缺口和恢复条件，并暂停迁移。条件恢复后重新核对迁移前提。只有用户改为普通批准，来源任务才可按协调规则和适配器的条件继续实施。

按[协调规则第 5 节](coordination-contract.md#5-executor-任务迁移)完成移交后，接手任务成为主任务，继续原流程，并沿用各步骤的启动条件。独立评审条件成立时，仍由独立 Reviewer 评审。

### 4.3 实施与返修

有 Spec 时，执行自主权与问题交回条件遵循 [工作记录规则的 Spec 标准](artifact-protocol.md#21-spec-artifact)：主任务收到设计问题后分析事实，按 Planner 路由补齐或修订规格；只有需要 Human 的实质决定或新增授权时才提问。没有 Spec 时，Executor 继续在明确目标与授权内自主实施，不为此强制生成 Spec。

环境或工具不可用时，只尝试已知可用、授权内且能满足同一目标的现有替代；继续尝试须有新证据或不同且可检验的假设。没有符合条件的下一步时，报告具体阻塞、已完成结果与恢复条件，停止受影响部分；独立工作继续。Adapter 对特定传输的限制仍须满足，不为穷尽可能性新增恢复机制。

主任务接收角色结果，将已批准方案交给 Executor。主任务继续处理同一范围内的返修、补证和复验，安排唯一负责方并完成已授权收尾。直接推进时，按[术语定义](terminology-contract.md#术语)中工作范围的定义处理。

## 5. 标记 Spec 完成和写入存档

用户明确请求存档时，主任务将其作为 `human-request` 交给 `document-project`。该请求授权按已确认的项目配置存档当前任务。能确定目标和改动均在授权范围内时直接写入。只请求存档时跳过 Spec。

用户请求把 Spec 标为已完成时，本次请求授权更新当前 Spec 的状态行。主任务按[Spec 完成规则](artifact-protocol.md#3-spec-完成)执行。

同时请求标记完成和存档时，沿用已有授权，先处理 Spec。按完成规则成功更新或返回 `no_op` 后，把存档作为 `human-request` 交给 `document-project`。Spec 处理失败时停止存档。存档受阻或失败时，保留 Spec 的已完成状态，并分别报告两项结果和继续存档所需条件。

正常实施时，先完成本次验收要求的文档。主任务满足“已完成”条件后，沿用第 4 节的实施批准，按[工作记录规则](artifact-protocol.md#3-spec-完成)把本次唯一已批准的 Spec 标为已完成。无 Spec 或用户要求保留原状态时跳过写入。状态编辑失败时保留实施完成证据并报告恢复条件。

## 6. 项目文档

用户明确调用 [`document-project`](../skills/document-project/SKILL.md) 时，直接使用当前请求作为技能输入。显式发布文档目标按[入口规则](intake-contract.md#41-用户明确调用)判断授权，再按该技能的参数和写入规则处理。其他请求继续遵循已确认的项目接入配置。Roadmap 调用该技能时，使用当前显式 Roadmap 请求和已形成的正文作为输入。

`on-request` 只响应明确的文档请求。项目配置为 `required-at-closeout`、本次唯一已批准的 Spec 已按第 5 节核实为“已完成”，且已有写入授权时，主任务才考虑自动存档。至少满足一项：

- 有值得长期查阅或维护的变更，例如后续会依赖的行为、接口、设计决定或运维方式。
- 后续代理或接手人需要快速掌握已核实的现状、关键取舍、限制或接手入口。没有持久产品变更时，这项仍可成立。

现有 Spec 或项目文档已能满足相同用途时直接引用。符合条件的内容交给 `document-project`，只写后续需要知道的信息。自动存档缺少授权，或文档内容、用途仍需要用户决定时，跳过存档并汇报任务结果。写入失败时保留完成状态并报告原因。验收明确要求的文档和用户明确提出的组合请求按第 5 节处理。
