# 协调规则

## 1. 范围与 Owner

本文规定如何划分工作、核对依赖和就绪条件、派发、等待、取消、接收结果及移交责任。术语见[术语定义](terminology-contract.md)，各步骤的启动条件和任务流程由[工作流规则](workflow-contract.md)规定。用户交互和记录分别遵循[交互规则](human-interaction-contract.md)和[工作记录规则](artifact-protocol.md)。
实际工作需要协调、委派、跨上下文移交责任或交回结果，或需要恢复时，读取本文。

Manager 在主任务内协调实际工作，完成后回到调用它的步骤。无需进入 Manager 的单个有界单元由主任务按同样规则直接管理。普通执行、迁移后的执行和 Explore 都使用下述规则。主任务仍负责角色流转、范围、授权、派发、集成和整个任务的结果。集成需要写入授权，正式裁决仍由独立的 Reviewer 作出。

## 2. 评估、拆分、依赖与就绪判定

将需要协作的工作划为可交付的工作单元。派发时明确目标、范围、授权、输入、负责方、输出边界和验证入口，有依赖时排定顺序。直接沿用仍有效的信息，无须另做一轮完整性审查。共享接口或初始化约定未定时，先做必要的最小调查，或合并无法独立完成的部分。下游只推进不依赖该前提的工作。

派发时按该单元实际难度、风险和隔离收益形成 Adapter 所需路由要求，使用下面的就绪条件确认输入；不单列预评估阶段。缺少会改变派发选择的事实时暂停该单元，已有判断仅在相关事实变化时重评。

主任务侧重方案、协调、授权与冲突处理、验收；自足的实施、集成和验证优先委派，确定性批处理复用脚本。上下文充分且委派成本更高的短小动作由主任务完成；难以隔离、检查或仍需共同推理的部分先保留在调用节点。后续成为独立工作包时重评，串行写入也可委派，不按文件数、型号、时长或代理数量强行拆分。

执行就绪（`execution-ready`）要求范围和验收已冻结，所需输入齐备、边界明确，授权和依赖均已满足，可以独立交付，且完成检查和验证职责明确。有 Spec 时，须提供精确引用，实施者须据此取得符合[工作记录规则](artifact-protocol.md#21-spec-artifact)的相关实施内容。派发消息不复制规格，设计未完成时不派发实施。无 Spec 时沿用已明确的目标，无须为派发补建。实施者负责局部检查，主任务安排共享验证。能够隔离的实施仍可并行。

研究就绪（`research-ready`）要求明确研究要支持的当前决定、结果接收方、问题、查询范围、所需证据和停止条件，输入和依赖也须齐备。研究默认只读，可以在实施范围冻结前开展。核心规则提出派发要求，适配器据此选择模型和调用参数。研究边界是否明确，和完成它的难度分别判断。

证据足以支持当前决定时交付；继续调查只针对会改变结论的剩余未知项及直接依赖。问题无法收敛或需越过查询范围时，返回已有事实、具体缺口和协调请求。未来阶段仅保留候选引用，除非已构成当前决定的必要依赖。

有 Spec 时，实施自主权与问题交回遵循上述 Spec 标准。跨单元接口、共享状态、初始化或验证前提需要变化时交主任务处理，独立工作继续。

独立工作默认新建代理。继续补证、返修或实施时，若目标和完成条件延续、授权相容、原决定、改动或证据仍影响本轮判断，且沿用历史的收益大于负担，优先复用原代理和模型。目标、写入范围或验收明显变化时重新判断。项目、领域、文件相同，或者代理空闲、有缓存，均不足以单独作为复用理由。也不得按消息数或上下文阈值自动换代理。新建时只交付可独立使用的输入与有效证据，并保持单一写入者。传输和容量由适配器处理。

## 3. 派发、等待、取消与单写入者

派发消息包含目标、允许范围、完成检查、停止及协调请求条件；研究另给问题、查询范围与预期证据，依赖或并发另给隔离边界。工作 root 与默认目录或 Skill 目录不同时，交付 root、规则、任务输入的精确入口及允许的外部 Skill/reference；接收方先读指定规则，避免从错误目录推导规则或搜索任务输入。

接收任务可由用户打开查看时，派发消息分别写清完成前要做的检查，以及用户打开任务后需要看到的结果。接收方按 [交互规则](human-interaction-contract.md#2-信息顺序与可见性) 在自己的会话中报告进度和结果。常规检查的原始结果保留在任务记录中。

Adapter 支持时，同级可直接交换范围内的事实、接口说明和证据，无需主任务逐条转发或抄送；否则沿现有返回路径交付。新目标、写入归属、继续/中断调度及共享验证与验收由主任务决定，约定变化返回协调请求。

中间消息只在接收方下一步需要变化时发送：冲突、失败、授权/接口变化、依赖就绪或正在等待的结果及时交付，已知相关事实与缺陷合并发送。其他发现随结果归并；不定时催报、确认收到、广播无关提醒、重发完整结果或用中断再继续探测进度。必要披露不受消息配额限制。

已有结果按当前问题交付事实、证据版本和剩余缺口；接收方核对适用性后仅补缺口或失效部分，沿用有效依赖清单。重新评审交付本轮差异和受影响证据，复用遵循[验收规则](assurance-contract.md)。

只读工作可以并行。同一文件或共享可变输出同时只允许一个活跃写入者。共享工作树内的生成物和公共结构也适用这项要求。Git 操作和整体验证保持串行。隔离工作树、补丁或候选实现可并行分析，由负责集成的一方串行应用。

共享可变环境同一时段仅一个操作者，可委派；其他单元继续独立工作。同环境、同产物且步骤确定的验证合并执行，固定该批输入；决定后续路线的最小检查优先，新失败交回决策者并按修复影响复验。环境操作与恢复遵循领域技能。

派发时明确局部检查、共享验证及结果接收者。按共享编译实际读取的源码、生成输入、配置和依赖判断写入是否冲突。启动前确认相关写入者已停止修改该批输入，并交回改动和待验证项。无法确认其他工作与这批输入互不影响时，继续等待。实施者可在交回后结束回合。主任务在输入稳定后安排合并检查，期间不派发修改这些输入的工作。

编译读到未完成输入时，保留原始结果、输入状态和待验范围，稳定后补验。错误归属须有证据；即使来自其他任务，也不免除本任务验证。稳定批次失败按归属返修，复用未受影响证据。

主任务对当前任务的工作范围持续调度，每波按就绪、依赖、授权、隔离和收益选择自行执行或单层派发：

```text
评估当前波次 → 串行执行或并行派发 → 聚合本波结果 → 重算剩余依赖图 → 下一波 / 阻塞 / 耗尽
```

串行只约束当前波次，返回后重算剩余依赖并保留未完成的集成、验证。依赖耗尽、无可推进单元并交付阻塞/恢复条件、命中停止条件或进入偏差处理时结束本次调度；根任务完成仍按整体条件判断。

反复依赖外部决定、接口变化或主任务补充时，收敛接口、调整波次或合并耦合部分，复用已有成果。稳定输入上的相关缺陷合并返修，决定路线的失败先处理。转移归属前确认旧写入者状态；影响范围、授权或验收才交 Human 决定。

派发后，主任务先做独立且不冲突的工作。目标已启动、下一步依赖其结果、结果由主任务接收，且没有其他可做的工作时，按当前任务、范围和隔离边界等待。

优先接收正常的完成通知。需要确认目标是否仍在运行时，按宿主适配器查询。收到新事实后重新核对依赖。目标任务的最终结果无须返回来源任务时，来源任务交接责任并给出目标任务引用后结束。

首次创建使用适配器规定的完整参数。不得用通用角色、默认继承或部分参数代替。参数不完整时进入偏差处理。按适配器的规则等待。需要取消时先中断，再核实停止状态。涉及写入时，须确认原代理和相关进程或工具已停止本次写入，才可确认取消完成或接管。超时不触发重复创建或流程转换。

返回消费者所需的结果/`delta`、已验证事实、实际验证、reference、风险、未知项、阻塞和协调请求，披露失败、未验证及范围/授权偏差。完整检索、源码和日志留在原始记录，按当前决定需要给精确片段；仅按工作记录规则保存有消费者的记录。消费与去重按第 6 节。

父任务核验关键原始证据及适用性，不重做仍由代理负责的完整调查。冲突、缺依赖或影响不明时优先补查具体问题。收到失败或验证缺口后，主任务按现有职责和授权完成可做的修正，或安排负责方补证，再按交互规则说明已处理的结果和仍待解决的具体条件。接管前须明确责任如何转移、原代理在哪些范围已停止。正式独立复核遵循验收规则。

## 4. Explore 研究

探索先沿用当前事实，再按第 1–3 节协调所需研究。把事实、冲突、未验证项和引用交回原步骤，由规划者判断是否足以定稿 Spec。显式探索的授权仅覆盖指定范围内的只读调查与协调。决定记录和界面草稿按[工作记录规则](artifact-protocol.md)处理。生产写入、定稿方案或验收、独立评审和外部动作按各自职责与授权处理。需改变范围、方案或补充授权时，只暂停受影响的动作，交回规划者或用户。

## 5. Executor 任务迁移

来源任务按[工作流的迁移规则](workflow-contract.md#42-执行任务迁移)暂停实施和写入派发。明确迁移批准和其他迁移前提均已确认后，才查询、复用或创建唯一目标，交付最小交接信息和必要引用。用任务或范围修订号、批准的 Spec 引用和本次工作流转移来区分候选。保留首次创建的原生标识，重试、重复批准或恢复时沿用唯一目标。不得另建跨会话注册表。

唯一目标取得项目规则、批准的 Spec、必要工作记录和证据，以及工具未携带的最小交接信息后，才接管主任务及剩余实施、评审、返修和收尾。目标沿用各步骤的启动条件和协调规则。来源任务给出原生目标引用后结束，无须等待目标返回。交接不复制完整对话。迁移标识、主任务职责和派发权均不交给委派代理。

移交前，查询、创建或交付失败时，来源仍是唯一负责的任务，并报告恢复条件。用户改为普通批准后，来源须按当前适配器核实本次迁移未成功创建目标任务、目标未接管，且同一范围没有其他写入者，才可恢复实施和写入派发。任一条件未满足或无法核实时，继续暂停受影响的实施和派发。移交后，由目标负责恢复、失败处理和结果，来源不得重新接管。对同一已完成的移交，只返回既有目标引用。无法证明目标标识或迁移前提时，停止迁移并报告偏差。

## 6. 完成、返回与偏差

Owner 保留目标、范围、授权和完成条件。每个委派单元/Role 对同一修订只回传一次结果，消费者只消费一次；原生传输不足以消歧时才补 任务或范围修订号、Source/Target、Owner 或去重信息，更正使用新修订号。

Feedback 的来源任务按[入口规则](intake-contract.md#4-入口决定)核对授权，不使用执行任务迁移的前提。反馈标识包含工作区、具体目标、Owner 及用户已提供的来源 reference。先按适配器核对已有标识、候选状态和交付记录。确实需要用户补充目标信息或选择处理任务时，才请求消歧。

唯一目标精确匹配且仍活跃或可恢复时，可以复用。如果同一反馈标识的任务已终止，且本次提交与该任务收到的原反馈完全相同，返回 `no_op` 和既有任务引用。其他已终止或过期的候选不算匹配。确认没有匹配时，在本次已有授权内创建一个目标，无须再次确认已取得的授权。

成功移交后，来源任务交付原生目标 reference 并结束，不等待或转述目标最终结果。调查代理只补充证据，不能接管反馈的 Owner、Role 或标识。目标任务按入口规则重新判断，继续通用流程。没有安全的移交路径时，来源任务保持 Owner，保留现场、原始错误和恢复入口，然后停止移交。

同一 `payload` 同时用于报告和回传完成结果时，只通过当前工具的完成路径向接收方交付一次。向用户报告时，只呈现已经接收并处理过的结果，表达遵循交互规则。

主任务结束本轮时，将当前任务结果归为以下三类。

| 结果 | 使用条件 |
| --- | --- |
| 已完成 | 目标、工作范围、必需验证、适用评审及其他阻塞验收均已满足。目标已满足且无须修改也归入这一类 |
| 暂停可继续 | 当前无法推进，且有明确的恢复条件。同一任务可在用户作出决定或授予所需授权、明确负责方、外部条件恢复或交付通道可用后继续 |
| 已结束但未完成 | 当前目标未全部达到，也已决定不再继续。例如用户或上游负责方明确取消、目标被替换、部分完成后停止，或外部系统终止且同一范围的安全恢复办法已经耗尽 |

未完成时，说明已完成部分、剩余事项、具体原因和证据。暂停可继续还须说明由谁解除阻塞、满足什么条件后从哪里继续。已结束但未完成时，说明决定停止的依据，以及日后恢复所需的条件（若有）。工作已经完成但必需结果无法送达时，保留工作完成的证据，说明交付缺口，并按能否恢复交付确定结果。确认整个任务已完成时，仍须满足必需的交付条件。已有记录按实际事实归入上述三类，无须改写历史标签。

执行任务迁移成功后，来源任务只报告交接结果。整个任务的结果由接手后的主任务判断。

Planner 提案获批且无其他阻塞时，主任务立即按[工作流的批准条文](workflow-contract.md#41-实施批准)处理本次批准。用户选择执行迁移时读[迁移条文](workflow-contract.md#42-执行任务迁移)。

有结果接收方时，核对其是否已接收并处理结果，以及当前传输需要的标识和实现基线（Baseline）。再核对流程是否已开始下一步，或主任务是否满足相应结果的条件。工具已绑定的标识不重复写入。任务迁移按第 5 节核对。

记录偏差时，保留预期、实际、影响、证据、恢复或停止条件，以及传输中缺失的必要标识。错误、过期或重复结果不触发额外写入、等待、流转或终态。环境不可用时按工作流规则的替代和停止条件处理。实施缺陷和属于实施者的补证交回原 Executor。正式评审发现的证据缺口按[验收规则](assurance-contract.md#3-评审结论与后续处理)交给唯一的证据负责方。研究失败、冲突或缺口交回调用步骤。旧写入者停止前不得另开写入者，也不得盲目重试。
