# 术语合同

> 状态：规范性核心术语合同

本文统一插件内提炼术语的定义。

## 术语

| 术语 | 定义 |
| --- | --- |
| 入口候选 | 初次判断或需求发生实质转折时，已有事实表明进入 Sacha 可能改变执行方式，但用户尚未决定是否接受；只用于一次性提议和避免重复提议，不表示已经接受 Sacha、打开决策关口（Gate）或取得授权。 |
| Direct | 当前主任务尚未进入 Sacha 的正式流程，在既有目标、范围、授权和验收内由当前上下文直接完成；仍须遵守适用的项目规则、使用领域能力并完成必要验证，需求发生实质转折并形成新的入口候选时重新判断。 |
| Scope（范围） | 当前目标包含的工作、须保留的行为、排除项与适用条件，由用户要求和已批准实施规格（Spec，若有）界定；范围本身不等于动作授权。 |
| Direct Scope | 当前任务围绕同一目标直接推进时采用的 Scope；预计文件列表只有在用户或已批准实施规格明确指定时才成为硬边界。 |
| Owner（负责方） | 对所指对象承担责任的位置或主体：规则与事实的 Owner 是其唯一负责文件或来源，工作的 Owner 是负责该工作结果的任务或代理。局部负责不表示取得主任务职责或额外授权；转移与协调由相应合同决定。 |
| 工作单元（work unit / 工作包） | 以可独立交付的结果为边界的一份工作；不与代理、文件、Spec 或 Artifact 数量一一对应。拆分、依赖、就绪与派发由协调合同规定。 |
| 主任务 | 当前负责整个工作流程并推进最终完成状态的用户任务；迁移成功后改指承担该职责的新任务。 |
| 单层派发 | 主任务创建全部委派代理（Agent）；每个委派代理都是主任务的直接子级，不调用 Manager，也不创建下级代理；迁移成功后改由新主任务执行。 |
| 委派 Agent | 主任务为一个工作单元创建的代理；只完成该单元并返回，不接管整个工作流程或派发权。 |
| 协调请求 | 委派代理需要继续拆分、协调依赖或增加代理时，向主任务返回重新评估所需的原因、候选单元、依赖或 `reference`；只定义返回含义，不新增状态、字段或工作记录（Artifact）。 |
| 普通批准 | 用户批准实施规格（Spec），但未明确选择由新任务执行。 |
| 明确迁移批准 | 用户批准实施规格，并通过选择项或同义表达明确选择由新任务执行；不表示执行任务迁移的前提已经满足。 |
| 可靠迁移信号 | 实施规格已经持久化且可访问，并存在可核实的运行环境上下文占用较高或压缩事实，或者存在不依赖未落盘对话、可观察的多阶段长历史；只决定用户审阅选项的推荐顺序。 |
| 执行任务迁移前提 | 用户已经明确批准迁移，实施规格已经持久化、可访问且获批，进入条件（Entry Condition）已经满足，当前主任务是唯一负责整个流程的任务，并且同一范围内没有正在写入的执行者；只用于批准实施规格后迁到新任务执行，不适用于 Feedback 的负责位置转移，也不改变已批准的实施规格、范围或验收。 |
| `base` | 用户或配置直接提供的目录；尚未表示解析、派生或验证后的实际生效目录。 |
| `root` | 从 `base`、配置或发现结果解析、派生并实际生效的目录；不得代指任意输入目录。 |
| `path` | 文件或目录在文件系统中的位置；用于可直接读取、写入或解析的文件系统目标。 |
| `reference` | 非文件形式的证据、负责位置、运行环境标识或间接指向；不得代替本应明确的文件 `path`，也不得另建 `locator` 作为同义术语。 |
| 显式发布文档目标 | 用户在明确的 `document-project` 请求中直接提供项目 `root` 内的 Markdown `path`，且文档类型为 `change-archive` 或 `system-guide`；不包括 Roadmap、Project Context、目录或 `root`，也不包括由项目接入（Project Integration）派生的目标。该术语只标识输入类别，授权、流转和写入动作仍归相应负责文件。 |
| Project Integration（项目接入配置） | 保存项目已确认规则入口、技能加载策略和相关文档位置等接入信息的配置，供角色定位项目约束与能力；不保存任务进度，也不替代具体动作授权。配置生成与更新由 setup-project 负责。 |
| 规范技能（canonical Skill） | 以当前运行环境技能目录中的 `name`、`description` 和 `path` 确定的唯一技能身份；不是别名、能力编号或技能内部工作单元。选择与加载规则由工作流合同和 setup-project 负责。 |
| 技能加载策略 | 项目接入中为规范技能确认的加载条件；只决定何时读取并采用技能，不表示已经获得授权、满足前置条件或执行动作。 |
| Project Context（项目上下文） | 供跨任务消费者使用的稳定项目术语与约束；不代替项目接入配置、任务进度或实施规格。内容维护与写入边界由 document-project 负责。 |
| Artifact | 供执行、恢复、复核或后续使用方继续工作的流程记录；不替代原始事实、用户授权或流程状态。 |
| Spec Artifact | Planner 根据已核实的项目事实和用户决定形成、经用户批准后作为实施与评审基线的目标项目实施规格；内容格式与权威关系由工作记录协议（Artifact Protocol）定义。 |
| 界面草稿 | 用于澄清布局、操作和状态变化的模拟界面；必要决定进入 Spec，草稿仅在被明确引用的范围内辅助实施与验收，不是第二份权威规格、独立流程状态或生产行为证据。制作与消费要求由 Artifact Protocol 定义。 |
| Roadmap | 面向项目用户和代理的自包含长期路线文档，保存目标、当前状态、阶段、依赖、完成信号、实施规格映射、接下来需要作出的决定、`Unknown` 和排除范围；不是工作记录或实施规格，不授予实施，也不保存 Sacha 内部流转。 |
| Spec 完成 | 当前任务进入 `goal_complete`，必需验证和适用评审均已满足后，把当前唯一已批准 Spec Artifact 的既有状态行原位标记为“已完成”；不移动、改名或生成新工作记录。 |
| 探索决定记录 | 实施规格形成前，保存后续规划或恢复会使用的已确认决定、未决项和最小恢复信息的工作记录。 |
| Execution Report | 保存实际变更、验证、偏差、风险和证据 `reference` 的可恢复索引。 |
| Review Artifact | 保存评审者判断、证据缺口和下一步流转的工作记录。 |
| Handoff | 供跨角色工作或恢复时继续使用的最小信息；不是流程节点或完成证据。 |
