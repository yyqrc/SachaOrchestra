# 术语定义

本文统一定义插件各部分共用的术语。

## 术语

| 术语 | 定义 |
| --- | --- |
| 直接处理（Direct） | 没有必要额外安排规划、协调、独立评审或交接时，在当前任务按目标和授权完成。仍须遵守项目规则、使用必要的领域技能并完成适用验证。目标或关键事实变化时重新判断受影响的工作。 |
| 工作范围 | 用户要求和已批准实施规格（Spec，若有）界定的工作、须保留的行为、排除项和适用条件。动作授权须另行核对。直接推进同一目标时，预计文件列表只有在用户或已批准实施规格明确指定时才成为硬边界。 |
| Owner（负责方） | 对规则或事实，指其唯一负责文件或来源。对工作，指负责该项结果的任务或代理。局部责任限于该项工作。主任务职责、动作授权、责任移交和协调均按相应规则确定。 |
| 工作单元（work unit / 工作包） | 以可独立交付的结果为边界的一份工作；不与代理、文件、Spec 或 Artifact 数量一一对应。拆分、依赖、就绪与派发由协调规则规定。 |
| 主任务 | 对整个工作流程及其最终结果负责的用户任务。迁移成功后，由接管流程的任务担任主任务。 |
| 单层派发 | 所有委派代理（Agent）均由主任务直接创建。委派代理不得调用 Manager 或创建下级代理。迁移成功后，派发由新的主任务执行。 |
| 委派 Agent | 主任务为完成一个工作单元创建的代理。它只负责该单元并交回结果，整体流程和派发仍由主任务负责。 |
| 协调请求 | 委派代理发现需要继续拆分、安排依赖或增加代理时，交回主任务重新评估。按需提供原因、候选单元、依赖或 `reference`。协调请求只是一类返回信息，不增加状态、字段或工作记录（Artifact）。 |
| 普通批准 | 用户授权在当前任务按已确认范围实施。使用 Spec 时，实施和验收沿用已批准的内容。 |
| 明确迁移批准 | 用户批准实施规格，并通过选择项或同义表达明确选择由新任务执行；不表示执行任务迁移的前提已经满足。 |
| 可靠迁移信号 | 实施规格已持久化且可访问，并至少有一类可核实的依据。运行环境的上下文占用较高或已经发生压缩，或者工作已经历多个可观察的阶段并积累了较长历史，继续工作无需依赖未落盘对话。用于判断是否值得向用户提出迁移。迁移仍须用户明确批准。 |
| 执行任务迁移前提 | 以下条件须全部满足。用户已明确批准迁移。实施规格已持久化、可访问且获批。进入条件（Entry Condition）已满足。当前主任务是整个流程的唯一负责方。同一范围内没有执行者正在写入。仅在批准规格后把实施迁到新任务时使用这些条件，Feedback 移交按自己的条件办理。迁移沿用已批准的规格、范围和验收。 |
| `base` | 用户或配置直接提供的目录；尚未表示解析、派生或验证后的实际生效目录。 |
| `root` | 从 `base`、配置或发现结果解析、派生并实际生效的目录；不得代指任意输入目录。 |
| `path` | 文件或目录在文件系统中的位置；用于可直接读取、写入或解析的文件系统目标。 |
| `reference` | 非文件形式的证据、负责位置、运行环境标识或间接指向；不得代替本应明确的文件 `path`，也不得另建 `locator` 作为同义术语。 |
| 显式发布文档目标 | 用户在明确的 `document-project` 请求中直接提供项目 `root` 内的 Markdown `path`，且文档类型为 `change-archive` 或 `system-guide`；不包括 Roadmap、Project Context、目录或 `root`，也不包括由项目接入（Project Integration）派生的目标。该术语只标识输入类别，授权、流转和写入动作仍归相应负责文件。 |
| Project Integration（项目接入配置） | 保存项目已确认规则入口、技能加载策略和相关文档位置等接入信息的配置，供角色定位项目约束与能力；不保存任务进度，也不替代具体动作授权。配置生成与更新由 setup-project 负责。 |
| 规范技能（canonical Skill） | 以当前运行环境技能目录中的 `name`、`description` 和 `path` 确定的唯一技能身份；不是别名、能力编号或技能内部工作单元。选择与加载规则由工作流规则和 setup-project 负责。 |
| 技能加载策略 | 项目接入中为规范技能确认的加载条件；只决定何时读取并采用技能，不表示已经获得授权、满足前置条件或执行动作。 |
| Project Context（项目上下文） | 供其他任务继续使用的稳定项目术语和约束。不得用它代替项目接入配置、任务进度或实施规格。内容维护与写入边界由 `document-project` 负责。 |
| Artifact | 供执行、恢复、复核或后续使用方继续工作的流程记录；不替代原始事实、用户授权或流程状态。 |
| Spec Artifact | 规划者根据已核实的项目事实和用户决定写成的实施规格。用户批准后，规格才成为实施和评审基线。格式和依据的优先顺序见[工作记录规则](artifact-protocol.md#21-spec-artifact)。 |
| 界面草稿 | 用于澄清布局、操作和状态变化的模拟界面；必要决定进入 Spec，草稿仅在被明确引用的范围内辅助实施与验收，不是第二份权威规格、独立流程状态或生产行为证据。制作与消费要求由工作记录规则定义。 |
| Roadmap | 面向项目用户和代理的自包含长期路线文档，保存目标、当前状态、阶段、依赖、完成信号、各阶段对应的实施规格、待决定事项、待查明的问题和排除范围；不是工作记录或实施规格，不授予实施，也不保存 Sacha 内部流转。 |
| Spec 完成 | 将当前唯一已批准 Spec Artifact 的既有状态行原位标记为“已完成”。进入条件、写入和失败处理见[工作记录规则第 3 节](artifact-protocol.md#3-spec-完成)。 |
| 探索决定记录 | 实施规格形成前，保存后续规划或恢复会使用的已确认决定、未决项和最小恢复信息的工作记录。 |
| Execution Report | 保存实际变更、验证、偏差、风险和证据 `reference` 的可恢复索引。 |
| Review Artifact | 保存评审者判断、证据缺口和下一步流转的工作记录。 |
| Handoff | 供跨角色工作或恢复时继续使用的最小信息；不是流程节点或完成证据。 |
