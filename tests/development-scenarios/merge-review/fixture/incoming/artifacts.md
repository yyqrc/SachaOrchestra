# Artifact Protocol（取样片段）

## 2. 渐进且最小

| Artifact | 生成条件 | 最小内容 |
| --- | --- | --- |
| 最终任务记录 | 同一上下文简单完成 | 修改、验证、失败/未验证与剩余风险 |
| 探索决定记录 | Spec 形成前已有确定决定供规划消费，或多轮/分支/压缩恢复需要保留探索锚点 | 已确认决定、依据/约束、未决项与 reference；恢复确需时增加原始问题、当前关注点、暂存思路，以及尚未探索/解决的实质分支、依赖与关键排除依据；疑似跨任务术语按需记录定义、排除含义、证据、边界、任务外消费者和 `Unknown` |
| Spec Artifact | 持久 Scope、批准方案或跨上下文恢复 | 目标项目实施规格；内容格式见第 2.1 节 |
| Execution Report | 续跑、证据索引或正式 Review | 实际变更（`delta`）、验证、偏差、风险、reference、恢复入口 |
| Review Artifact | 正式 Review | 问题、裁决结果（Outcome）、证据缺口、下一路由 |

实施者在写入前确认目标范围内的已有改动。调用会修改文件的 MCP 前，必须读取该 MCP 随插件发布的工具文档，确认修改文件信息是由写入回执返回还是需要查询取得，以及字段、比较范围、完整性和失败后的收集方式；文档位置由当前领域 Skill 或 MCP 工具说明提供，不假定另一 Skill 已执行。已有读取仍适用于当前工具版本时复用；文档或文件信息接口缺失时记录具体缺口，并用明确范围的写入前后文件状态或版本控制差异补查，不猜测字段或查询工具。

每次直接编辑、MCP 写入、外部工具或生成链执行后，合并实际新增、修改、删除文件，并与该范围的文件状态或版本控制差异核对。重命名保留原路径和新路径；既有改动、未发生内容变化的输出、备份与临时文件不混入本次正式改动。失败或超时也须核对已经发生的文件变化；回执缺失、截断或范围外写入时保留具体缺口，不能把预期输出目录、样例文件或宿主的“已编辑文件”卡片当作完整清单。

最终任务记录与 Execution Report 的实际修改使用上述核对结果；交接时随既有记录传递文件路径、变更类型、写入来源和必要证据。没有持久记录消费者时在当前交付中承载，不为收集文件另建任务状态或强制生成报告。Human 可见展示沿用 [Human Interaction Contract](human-interaction-contract.md#2-信息顺序与可见性)。

### 2.1 Spec Artifact

Spec Artifact 面向目标项目的 Human、Executor 和 Reviewer。只给三者项目规则、项目事实和 Spec 时，必须仍能理解目标、边界、方案与验收；移除 Sacha 上下文不得改变其技术含义或可执行性。
