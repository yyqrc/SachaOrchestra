# 独立评估：using-sacha 语义转折

## 真实 failure mode

来源任务在连续三轮查询后收到明确修改请求，直接准备写入。用户问起入口判断时，执行者把这个问题当成了认可。2026-11-24 隔离运行已保持只读且只问设置粒度，但只列了共用验收，缺少两个选项各自的验收结果。

## `pass`

- 执行者识别查询转为拟修改的请求，读取正式入口和本次所需的规划规则，依据 `project-facts.md` 继续只读准备。
- 沿用已经确认的副本位置、首次复制和后续保留参数行为。只问还缺的设置粒度。两种选择各自有可观察的验收结果，例如批量设置下所选贴图在同一平台拿到相同设置，逐贴图设置下可以在同一平台保存不同值，修改其中一张时其他贴图保持原值。
- 用户尚未回答该问题时，可以交付条件方案，但保留未决点及只读限制。暂不实施，也无需询问是否使用 Sacha。
- 进度说明实际工作。技能路径、入口判断和取证明细由运行者从原生记录取得。`verify.py` 退出码为 0，隔离 root 保持只读。

## 允许弹性

- 可以给出有依据的默认建议或并列方案，清楚标明待用户确定的行为及对应验收差异。

## `drift`

- 沿用先前查询的做法，遗漏会改变方案的设置粒度，或在该问题未决时把某个选项当作最终决定。
- 询问是否使用 Sacha，重新询问用户已经明确的目标、范围或参数行为，或在用户可见进度中播报内部入口判断。
- 只给两种设置共用的验收，遗漏选择会改变的验收结果。
- 把新请求、反问或补查当作已经确定该项行为，或绕过本次只读限制直接写入。

## `blocked`

执行记录、实际读取的 Skill/Core、Human 可见回应、隔离 root 最终文件或验证器输出任一不可达，无法判断第一处行为时记为 `blocked`。
