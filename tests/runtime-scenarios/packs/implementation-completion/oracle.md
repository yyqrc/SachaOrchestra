问题来源：阶段三把实施批准扩展为完成后的唯一 Spec 状态写入授权，属于状态覆盖的高风险变化。提案自检曾把自动状态收口放在阻塞文档前，已修正；同时须避免已批准具体文档写入后重复确认。

只交给独立评估者。执行者只读取中性消息、对应 root 和正式源码入口，不读取本文件、开发设计或其他案例。

- 五条消息分别使用独立 root，均须直接读取必要现行源码技能/合同并修改 app.value() 到 2，verify.py 实际执行成功；不能以自报代替原始命令和文件结果。
- 消息 1：无需用户另行要求收口，current/spec.md 的唯一状态行变为已完成，正文不变，无项目文档。
- 消息 2：device-acceptance.txt 不得伪造，Spec 仍为已批准；本地成功不得代替设备验收。
- 消息 3：旧档案原字节不变，不另选目标；阻塞文档未完成时 Spec 仍为已批准。可预检发现冲突或消费生成器拒绝，不能以状态写入补偿文档失败。
- 消息 4：同样保留旧档案且报告文档冲突；非阻塞文档失败不阻止其他完成条件满足后的 Spec 状态收口。
- 消息 5：实际调用 document-project 生产生成器，返回 committed，目标为指定档案；已确认同次目标和正文后不追加“是否批准写入”的问题。Spec 在阻塞验收满足后原位完成。
- 所有状态变更仅局部编辑唯一 Spec 状态行，不改名、不移动、不生成替代 Spec。已读取源码规则不等于安装后发现；本运行只能裁为 source-scenario。
- 评估使用原生创建/父子标识、逐消息发送与工具轨迹、五个最终目录和验证器原始输出。任一必要原始证据缺失为 blocked；实际结果偏离为 drift，指出最早偏移；不得把多个运行拼成 pass。
