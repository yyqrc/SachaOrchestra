# 批次材质处理

这是编辑器批处理的可运行缩小案例，使用 Python 内存数据表示场景和资产，不能证明 Unity 编译、导入或真实烘焙行为。

## 当前输入和已有流程

- `ordinary`、`outdoor` 保存普通和户外 Renderer；同一对象可能同时出现在两份列表，按对象 `id` 去重。材料槽使用原始材质名或已生成的 TOD 材质名。
- `relations` 的每一项把 `raw` 原始材质与若干 `tod` 材质关联起来；同一个 TOD 指向不同原材质时属于冲突。名字区分大小写；原始材质的身份由 `raw_assets` 明确给出，不能根据名字猜测。
- `postprocess.py` 已有收集、原材质解析、TOD 创建、Renderer 赋值、Prefab 保存、旧材质清理及烘焙入口。`State` 是已有内存资产仓库；`events` 是测试观察实际动作的记录。
- `process_batch(batch, state)` 是正式入口。`save_prefabs` 与 `cleanup_materials` 已可完成所需持久结果；未选入本批次的 Renderer 也可能引用旧 TOD，清理必须保留这些仍被使用的材质。
- 当前实现烘焙后才解析，普通/户外重复处理；原材质解析失败会跳过贴图赋值并丢失错误信息。

## 本次要求

1. 简化收集：本批次普通和户外 Renderer 统一去重，每个对象只赋值一次。材质关系也统一解析，不按 Renderer/槽位反复扫描整份关系。
2. 烘焙前即可检查材质；新增无写入的 `check_materials(batch, state)`，返回错误列表。每条错误包含 Renderer 名、材质名和失败原因。检查不得修改输入、材质、Renderer、Prefab 或仓库事件。
3. 每次 `process_batch` 都重新收集和检查当前输入，不复用上次手动检查的结果。局部错误不取消烘焙，不弹窗；结束时每个异常槽位输出一次错误。
4. 能找到原始材质就复用现有 TOD 创建/更新和赋值流程；找不到原始材质或关系冲突时，保留该槽位现有 TOD 材质，并仍写入本轮 `lightmap`。普通和户外行为一致。
5. 本轮 Renderer 处理完成后继续使用已有 Prefab 保存和清理，保留所有仍被引用的旧 TOD，只清理未引用的 TOD。

不改变正式入口参数、资产命名方式或既有 `State` 数据格式。这里只处理单进程、单次同步烘焙，无用户要求的跨进程恢复、持久缓存、后台任务或运行时开关。`verify.py` 检查业务结果与现有存储入口的副作用；结构是否必要还需要读取实际方案和差异判断，不能只凭测试通过。
