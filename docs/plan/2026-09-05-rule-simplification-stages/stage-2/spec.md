## 目标

采用以下行为调整，不将其称为纯文字等价替换：

1. 普通开发不因文件属于规则、工作量大或存在证据缺口就自动进入 Sacha 产品 Gate；已明确采用 Sacha 时继续按其现行合同。
2. 只有依赖用户重新决定的变化才暂停相应写入；同范围修复、补证和已批准变化持续处理。新增高层能力仍先批准，保留设计到使用方的修改顺序。
3. 不将交付前“再次确认”解释成再次询问用户。仍要核对机制依据与相邻约束；仅依据变化时修正或提出新决定。
4. 参数只有需要用户或环境选择时才放进配置；无需调整的实现常量可留在代码。机械步骤只有脆弱且重复时才脚本化，不为规整而增加包装或配置层。

## 保留要求

- 发布插件的规则、引用与必要运行语义须在发布 root 内自包含；开发文档和个人技能不能替代。
- 单层派发、独立复核、授权、去重、恢复与任务完成的产品含义不在本阶段改变。
- 新机制须有真实问题、唯一负责文件、实际使用方、会改变的判断和无效条件；删除重复手续不取消这些依据。
- 共享术语在插件内定义，开发侧维护索引；开发专用术语与单任务决定仍分别放置。修改含义后同步使用方和相关索引，不引入第二份完整定义。
- 已确认的场景触发条件保留：真实行为回归、高风险后果不宜等待日常暴露，或用户明确要求实际运行验收。未触发的运行检查不自动成为待补任务。
- 场景的隔离目录、执行者与评估者输入隔离、原生证据和失败结果依然按 tests/runtime-scenarios/README.md 执行，不能由静态测试或自报替代。
- 生产脚本测试仍在隔离临时目录调用真实入口，并验证可解析状态；按实际风险选择案例不允许污染用户工作区或省略机器结果检查。
- 源码、结构、测试、包、安装后发现、运行与人工验收的证据范围分开陈述。
- 安装、发布、市场、外部动作和 Git 操作的授权不扩大；本次只批准内容修改时不执行这些动作。

## 发版提速的事实与实施要求

- 当前 docs/release.md 虽允许复用 Review，但仍默认先 prepare；scripts/release.py:407–418 每次根据暂存文件生成并执行检查，没有消费过去测试结果的入口。只有版本文件变化时不映射代码回归，完整实现仍在暂存区时会重新选中相关模块。
- scripts/release.py:349–355 对 DSH 范围选择 tests/validate_dsh_companion.py；该脚本第 185–195 行调用 pnpm verify 和 pack，package.json 的 verify 包括 typecheck、全部测试、build 和 preview:build。若这些结果仍有效，发版再次执行会重复工作。
- 现有 publish 第 443–500 行只做 candidate/release 身份检查、提交、标签、原子推送和远端核对，已有分阶段耗时输出，动作直接复用。第 564 行必填 --review 仅接受 reused/accepted，不能如实表示现行 Gate 关闭的情况；增加显式 not-required，不把无需正式评审写成已通过。该参数只记录判断，不证明评审或赋予发布授权，不新增回执、缓存或 Hash 协议。
- 普通与快速发版统一默认路径：确认范围和已有证据 → 更新版本与实际需要的发布说明 → 精确暂存 → publish → 交付机器结果。README 的入口或用法没有变化时不为发布而强制修改。
- 版本、发布状态或纯发布说明变化不因 tree 改变就触发代码回归或新 Review；行为变化、验收输入变化、失效证据或已知问题才补对应部分。不可把明确失败或缺失的必要证据当作已验收。
- prepare 保留为现有补验入口，不再成为默认前置；少量缺口使用对应现有测试命令，并通过现有 staged_snapshot 导出同一暂存树的隔离快照，保留 tree 与原始结果，避免读取范围外工作区或重跑其他有效检查。独立 DSH 配套包的构建和安装不自动成为主插件发布步骤。
- 保留暂存范围匹配、冲突检查、候选与 tag 身份、原子推送、远端核对和失败恢复；它们保护实际发布对象，与重新做实施验收不同。
- 本轮不执行发版、安装或耗时基准，不承诺包含网络与外部环境的固定分钟数。历史 0.12.7 的记录显示发版期间还发生范围重建、验证器与源码修复及新增语义评审，不能把整个任务时长当作 publish 命令耗时。

- 历史记录保持冻结，已有真实验证不被新的规则措辞追溯否定；本阶段不清理历史、缓存或未跟踪内容。
